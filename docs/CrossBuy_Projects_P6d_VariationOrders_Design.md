# CrossBuy — المشاريع والمقاولات — P6-د: أوامر التغيير (Variation Orders) — تصميم فقط

> **الحالة:** تصميم بانتظار مراجعتك. **لا كود بعد.** بند حسّاس (يعدّل نطاق عقد قائم). يُبنى فوق: Project + BOQ (P1) + الإنجاز (P3) + المستخلصات (P4). **تشغيلي/تقديري — صفر قيود؛** الأثر المالي يأتي لاحقًا عبر المستخلصات/الصرف على البنود الجديدة.

---

## 1. النطاق والمبادئ
- **أمر التغيير** = زيادة/نقص في نطاق الشغل (بنود BOQ جديدة و/أو تعديل كميات/أسعار بنود قائمة) بقيمة (+/−) وسبب وحالة، مربوط بالمشروع.
- **صفر قيود محاسبية** لأمر التغيير نفسه (نطاق تقديري). لا كاتب جديد. بـ `ProjectId`.
- **المستخلصات السابقة لا تتأثر** (تحققتُ: `PreviouslyBilled` = Σ `PeriodValue` **المخزّن** من سطور المستخلصات المرحّلة — لقطات، لا يُعاد حسابها).
- **`inv-test-integrity = 0`** (لا يُمسّ — لا قيود).

---

## 2. نقاط الحسم (خيارات + توصية)

### 2-1 كيان أمر التغيير + نطاق التعديل
**✅ التوصية:** `VariationOrder` (رأس: ProjectId, VoNo, Description, Reason, Value(+/-) **مشتقّة من السطور**, Status **Draft/Approved**, Date) + `VariationOrderLine` بنوعين:
- **New:** بند BOQ جديد (Code/Description/Unit/Qty/UnitPrice + تكاليف مواد/عمالة/باطن/معدات).
- **Adjust:** تعديل بند قائم (`BoqItemId` + **لقطة القديم** OldQty/OldUnitPrice + الجديد NewQty/NewUnitPrice).

**الحالة:** Draft (تحرير، **بلا أثر**) → **Approved** (يُطبَّق على BOQ + يُحتسب في قيمة العقد المعتمدة). لا حذف بعد الاعتماد (يُعكس بأمر تغيير مضاد). قيمة الأمر = Σ(قيمة البنود الجديدة) + Σ(فرق التعديلات: New − Old) — **مشتقّة تلقائيًّا** لا يدوية (منعًا للتضارب).

### 2-2 قيمة العقد: الأصلية مقابل المعتمدة
| الخيار | الوصف | العيب |
|---|---|---|
| أ) تعديل `Project.ContractValue` مباشرة | قيمة واحدة متغيّرة | يفقد الأصل (تدقيق ضعيف) |
| **ب) الأصلية ثابتة + المعتمدة مشتقّة (موصى به)** | `ContractValue` = **الأصلية** (لا تتغيّر) · **المعتمدة = الأصلية + Σ أوامر التغيير المعتمدة** (تُحسب عند القراءة، بلا عمود جديد) | — |

**✅ التوصية: (ب).** `Project.ContractValue` يبقى **الأصل الثابت**؛ القيمة المعتمدة = الأصلية + Σ VO المعتمدة، تُعرض في الشاشات وتُستخدم في مقارنة BOQ/الموازنة. **المقدّم (Advance%) يبقى على قيمة العقد الأصلية** (المقدّم يُتفق عليه ابتداءً)؛ الاحتجاز نسبة على قيمة العمل بالمستخلص (لا يتأثر). فلا حاجة لتغيير منطق P2/P4.

### 2-3 تمييز بنود التغيير عن الأصلية
**✅ التوصية:** عمود **`VariationOrderId`** (nullable) على `BoqItem`:
- **null** = بند أصلي.
- **مضبوط** = بند مضاف بأمر تغيير (عند اعتماد VO تُدرَج بنوده الجديدة موسومةً بـ VoId).
- **التعديلات (Adjust):** تُطبَّق **في مكانها** على `BoqItem` القائم (Qty/UnitPrice)، والتدقيق (قديم→جديد) محفوظ على `VariationOrderLine`. (البند القائم يبقى `VariationOrderId=null` — أصلي معدّل، والتاريخ على الـVO.)

### 2-4 الأثر على الإنجاز والمستخلصات (بلا كسر — تحققتُ)
- **البنود الجديدة** (leaf) تدخل **تلقائيًّا** قياس الإنجاز التالي والمستخلص التالي (لأنها `BoqItem` — كشف الأوراق في `ProgressService`/`ProgressBillingService` يلتقطها).
- **القياسات السابقة:** لم تتضمّن البنود الجديدة (تراكميها السابق = 0) → لا أثر.
- **المستخلصات السابقة:** `PeriodValue` **مخزّن (لقطة)** → **لا يتغيّر** بأي تعديل/إضافة لاحقة. المستخلص التالي = التراكمي الحالي − المفوتر سابقًا (المخزّن) → لا ازدواج ولا كسر.
- **تعديل سعر بند قائم:** المستخلصات المرحّلة (لقطات) لا تتأثر؛ المستخلصات القادمة والنسبة المرجّحة تستخدم السعر الجديد **من تاريخ الاعتماد فصاعدًا** (هذا السلوك الصحيح لأمر التغيير).

### 2-5 لا أثر محاسبي مباشر
**✅ اعتماد أمر التغيير = تشغيلي فقط** (تعديل/إضافة BoqItems + تسجيل الـVO) — **صفر قيود يومية**. الأثر المالي يأتي حصريًّا عبر المستخلصات (P4) والصرف (P5) اللاحقة على البنود الجديدة/المعدّلة. **يُتحقَّق في p6d-test بثبات عدد القيود.**

## 3. نموذج البيانات (إضافي)
- عمود **`BoqItem.VariationOrderId`** (int? nullable) — null=أصلي.
- **`VariationOrder`** (ID, CompanyID, ProjectId, VoNo, Description, Reason, Value, Status, CreatedAt/By, ApprovedAt/By).
- **`VariationOrderLine`** (ID, VariationOrderId, Kind[New/Adjust], BoqItemId?, Code, Description, Unit, Qty, UnitPrice, Material/Labor/Subcontract/Equipment, OldQty?, OldUnitPrice?). SQL `deploy/sql/projects_p6d_variation.sql` (CREATE + ALTER add VariationOrderId).

## 4. الخدمة `IVariationOrderService`
- `GetForProjectAsync` / `GetAsync` / `SaveDraftAsync` (رأس + سطور، يحسب القيمة) / **`ApproveAsync`** (يُدرج بنود New في BOQ موسومةً بـ VoId + يطبّق Adjust على البنود القائمة مع لقطة القديم؛ **صفر قيود**) / `RevisedContractValueAsync(project)` = الأصلية + Σ VO المعتمدة. حرّاس: لا تعديل/حذف بعد الاعتماد.

## 5. الشاشة (بانتظار تصميمك — لا أجتهد)
نقطة الدخول: زر «أوامر التغيير» على صف المشروع. قائمة أوامر التغيير + محرّر (رأس: وصف/سبب + سطور New/Adjust بنمط سطور BOQ) + زر «اعتماد». عرض: قيمة العقد الأصلية / Σ أوامر التغيير / القيمة المعتمدة.
**سؤالي:** أطبّق النمط (قائمة + محرّر سطور بنمط BOQ + بطاقة «الأصلية/التغييرات/المعتمدة»)؟ أم نمط آخر؟

## 6. اختبار DevSeed المخطّط: `/api/dev/p6d-test`
مشروع + BOQ أصلي + قياس/مستخلص أول (لقطة) → **أمر تغيير معتمد** (بند جديد + تعديل سعر بند قائم) → يتحقّق:
- **صفر قيود** من اعتماد أمر التغيير (JE count ثابت).
- البند الجديد **موسوم VariationOrderId** وظهر في leaf BOQ؛ التعديل طُبِّق مع لقطة القديم على الـVO line.
- **القيمة المعتمدة = الأصلية + قيمة الأمر**.
- **المستخلص السابق لم يتغيّر** (PeriodValue المخزّن كما هو)؛ قياس/مستخلص جديد يلتقط البند الجديد بلا ازدواج.
- **`inv-test-integrity=0`**. ينظّف نفسه.
