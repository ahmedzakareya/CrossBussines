## 0) الرؤية والمبادئ الحاكمة

**الرؤية:** نظام مهام للموظفين، كل مهمة تستهلك وقتًا (تايم شيت)، والوقت يخدم ثلاثة مخرجات:
**إنتاجية** (تقارير أداء) + **تكلفة** (تكلفة مشروع/أمر تشغيل) + **مرتبات** (ساعات تغذّي الأجر).

**المبادئ (ثوابت لا تُكسر):**
1. **لا كاتب محاسبة جديد.** أي قيمة مالية (تكلفة/فاتورة/مرتب) تمرّ حصريًّا عبر الخدمات القائمة: `JournalEntryService` · `ReceivableService` · `ManufService` (للعمالة على أوامر التشغيل) · موديول المرتبات القائم.
2. **`inv-test-integrity` = 0** بعد كل مرحلة. المهام والتايم شيت **تشغيلية بلا أثر محاسبي** حتى لحظة «تحويل الوقت لقيمة» التي تستدعي خدمة قائمة.
3. **إعادة الاستخدام قبل الإنشاء:** نتبنّى الأنماط المُثبتة في الكود (الربط polymorphic، جداول الأدوار لكل موديول، الخدمات الخلفية الدورية) بدل اختراع أنماط جديدة.
4. **واجهة Metronic خالصة** + كل النصوص من resx + معيار المشروع (Swal confirm ثم toastr لكل حفظ/حذف) + بحث حقيقي + لا بيانات ثابتة (حسب قواعد المشروع القائمة).

**خريطة التكامل مع ما هو مبنيّ فعلًا (بأسماء حقيقية من الكود):**

| نحتاج | الموجود فعلًا في الكود | الملف |

## 1) كيان المهمة (Task)

### الحقول المقترحة
`Task { ID, CompanyId, Title, Description?, AssigneeEmployeeId, CreatedByEmployeeId, Priority, DueDate?, Status, EstimatedHours?, ActualHours (محسوب), EntityType?, EntityId?, ProjectId?, IsBillable, BillRate?, CustomerId?, CreatedAt, CompletedAt? }`

- **الأولوية `Priority`:** `Low | Normal | High | Urgent`.
- **الوقت المقدّر `EstimatedHours`:** يُدخله المُنشئ. **الوقت الفعلي `ActualHours` = Σ سطور التايم شيت** (محسوب، لا يُدخل يدويًا — مصدر حقيقة واحد).
- **`IsBillable`/`BillRate`/`CustomerId`:** لدعم الفوترة (TM-5) — تبقى فارغة للمهام الداخلية.

### آلة الحالة `Status`
| الحالة | متى | الانتقال |
|---|---|---|
| `New` (جديدة) | عند الإنشاء | → InProgress |
| `InProgress` (شغّالة) | أول تسجيل وقت أو بدء يدوي | → Done / Blocked |
| `Blocked` (متوقفة) | عائق (اختياري) | → InProgress |
| `Done` (خلصت) | إنهاء المسؤول | نهائية (يفتحها المدير للمراجعة) |
| **`Overdue` (متأخرة)** | **حالة مشتقّة لا مخزّنة** = `DueDate < الآن && Status ∉ {Done}` | تُحسب عند العرض |

> **نقطة حسم 1-أ — «متأخرة» مخزّنة أم مشتقّة؟**
> - (أ) مشتقّة عند العرض (لا حقل).  ← **موصى به:** لا تكرار بيانات، لا وظيفة تحديث ليلية.
> - (ب) حقل مخزّن يُحدَّث بخدمة دورية.
> **التوصية:** (أ) مشتقّة؛ لو احتجنا فرزًا/إشعارًا بالمتأخر نضيف علمًا اختياريًا لاحقًا في TM-7.

> **نقطة حسم 1-ب — كيان جديد أم إعادة استخدام `Crm.Activity`؟**
> - (أ) توسيع `Crm.Activity` الموجود (فيه Subject/DueDate/Done/Owner/EntityType).
> - (ب) **كيان `Task` جديد مستقل** يتبنّى نفس أنماط `Activity` (polymorphic + owner + reminder).
> **التوصية:** **(ب) كيان جديد.** `Activity` مربوط بمفاهيم CRM (Lead/Opportunity) وبلا وقت مقدّر/فعلي ولا تايم شيت ولا تكلفة/فوترة/حالة غنية. نبني `Task` مستقلًّا **بنفس نمط الربط والمالك والتذكير** المُثبت في `Activity` (اتساق بلا تحميل CRM بما لا يخصّه). نتركهما منفصلين كما فصلنا الموديولات.

### المرفقات والتعليقات
- `TaskAttachment { ID, TaskId, FileName, FilePath, UploadedByEmployeeId, UploadedAt }` — يتبع اصطلاح الرفع القائم (`wwwroot/uploads/...`).
- `TaskComment { ID, TaskId, EmployeeId, Body, CreatedAt }` — خيط تعليقات بسيط.

## 2) الربط بسجلات النظام (Polymorphic)

### التخزين
حقلان على `Task`: **`EntityType` (نص) + `EntityId` (int)** — نفس النمط المُثبت في `Crm.Activity.EntityType/EntityId` و`JournalEntry.SourceType/SourceId`.

> **نقطة حسم 2-أ — شكل التخزين**
> - (أ) **`EntityType`+`EntityId` واحد** (سلسلة نوع + معرّف). ← **موصى به:** مُثبت في الكود، مرن، بلا تغيّر سكيمة عند إضافة نوع.
> - (ب) أعمدة FK منفصلة لكل نوع (`InvoiceId?`, `CustomerId?`, `WorkOrderId?` ...). أوضح مرجعيًّا لكنه يتضخّم مع كل نوع.
> - (ج) جدول ربط منفصل (M:N). زائد عن الحاجة (المهمة تُربط بسجل واحد).
> **التوصية:** (أ)، مع **قائمة بيضاء للأنواع** + **مُحلِّل روابط (Link Resolver)** يترجم `(EntityType, EntityId)` إلى: الاسم المعروض + رابط الشاشة العميق (deep-link).

### الأنواع المدعومة في الإطلاق
| `EntityType` | يفتح على | مثال استخدام |
|---|---|---|
| `SalesInvoice` | فاتورة المبيعات | «حصّل الفاتورة المتأخرة» |
| `PurchaseInvoice` | فاتورة المشتريات | «راجع فاتورة مورد» |
| `Customer` | كارت العميل | «اتصل بالعميل» |
| `ManufWorkOrder` | أمر التشغيل | «راجع جودة أمر التشغيل» |
| `PosOrder` | طلب المطعم/التوصيل | «وصّل الطلب» |
| `Employee` | كارت الموظف | «جهّز أوراق موظف جديد» |
| `Project` | المشروع | مهمة على مشروع |
| `Item` | الصنف | «اطلب صنفًا ناقص المخزون» |

- **بلا FK قاعدة بيانات** (نوع نصّي) — لكن الحذف الآمن يُدار بالمُحلِّل (لو السجل غير موجود يعرض «سجل محذوف» بدل رابط مكسور).
- الموظف يفتح المهمة → يضغط الرابط → يذهب للسجل مباشرة.

## 3) التايم شيت (Timesheet)

### الكيان
`TimesheetEntry { ID, CompanyId, TaskId, EmployeeId, Date, Hours, Description?, Source, StartedAt?, EndedAt?, IsBillable, CreatedAt }`
- **`Source`:** `Timer` (مؤقّت حيّ) | `Manual` (إدخال يدوي).
- **الوقت الفعلي للمهمة = Σ `Hours`** لكل سطورها (يُعاد حسابه عند أي تغيير).

### المؤقّت الحيّ (ابدأ/قف)
> **نقطة حسم 3-أ — أين يعيش المؤقّت؟**
> - (أ) **الخادم يخزّن سطرًا مفتوحًا** (`StartedAt` مضبوط، `EndedAt`=null) = «قيد التشغيل»؛ عند «قف» يُضبط `EndedAt` وتُحسب `Hours` = الفرق. ← **موصى به:** يصمد أمام إغلاق المتصفح/تبديل الجهاز، ومصدر الوقت هو الخادم (لا تلاعب بساعة العميل).
> - (ب) ساعة إيقاف في المتصفح فقط تُرسل الناتج عند «قف». هشّة (تُفقد بالإغلاق).
> **التوصية:** (أ). **قاعدة: مؤقّت واحد نشط لكل موظف** — بدء مؤقّت جديد يوقف السابق تلقائيًّا (يمنع ازدواج الوقت).

### الإدخال اليدوي
نموذج: مهمة + تاريخ + ساعات + وصف. تحقّق: `Hours > 0` ومعقولة (≤ 24/اليوم مثلًا). يظهر في نفس شبكة سطور المهمة.

> **نقطة حسم 3-ب — «قابل للفوترة» على مستوى السطر أم المهمة؟**
> - (أ) على المهمة فقط. أبسط.
> - (ب) **على السطر** (`IsBillable` لكل سطر، يرث افتراضه من المهمة). ← **موصى به:** واقعي (بعض ساعات مهمة واحدة غير قابلة للفوترة).
> **التوصية:** (ب) مع وراثة الافتراض من المهمة.

## 4) تحويل الوقت لقيمة (عبر الخدمات القائمة فقط)

### 4-1 التكلفة
- **تكلفة الساعة للموظف** = `Employee.ManufHourlyRate ?? (BaseSalary ÷ PayrollSettings.StandardMonthlyHours)` — **نفس** اشتقاق `ManufService.AddLaborAsync`.
  > **نقطة حسم 4-أ — نكرّر المنطق أم نستخرجه؟**
  > **التوصية:** استخراج **`IEmployeeCostService.HourlyCostAsync(employeeId)`** مشترك، ثم إعادة توجيه منطق `ManufService` إليه (مصدر حقيقة واحد لتكلفة الساعة) — استخراج بلا تغيير سلوك.
- **إلى أين تذهب التكلفة؟**
  > **نقطة حسم 4-ب — أثر التكلفة**
  > - (أ) **تكلفة تقريرية فقط** (Σ ساعات × تكلفة الساعة، تظهر في تقرير المشروع/الأمر) بلا قيد GL. ← أبسط، يحافظ على الثوابت بلا أي قيد.
  > - (ب) **مهمة مربوطة بأمر تشغيل** → تُغذّي **سطر عمالة عبر `ManufService.AddLaborAsync` القائم** (Dr WIP / Cr أجور) — كاتب قائم، الثوابت سليمة.
  > - (ج) مهمة مربوطة بمشروع → قيد تكلفة عبر `JournalEntryService` بحمل `ProjectId` (Dr مصروف مشروع / Cr مستحق أجور) — عند طلبك فقط.
  > **التوصية:** **TM-4 = (أ) تقريري افتراضيًّا**، + تفعيل (ب) للمهام المربوطة بأمر تشغيل (لأن الكاتب جاهز والحساب موجود). (ج) خيار لاحق عند الحاجة. لا كاتب جديد في كل الحالات.

### 4-2 الفوترة
- الساعات القابلة للفوترة لعميل → **فاتورة بالساعة عبر `ReceivableService.CreateSalesInvoiceAsync`**:
  - سطر `SalesLineInput { ItemDescription = اسم المهمة/الوصف, Qty = مجموع الساعات القابلة للفوترة, UnitPrice = BillRate, RevenueAccountId = حساب إيراد الخدمات, ItemId = null, WarehouseId = null }` — **بلا صنف/مخزون** (خدمة) → لا حركة مخزون، فقط إيراد + ضريبة + ذمم.
  > **نقطة حسم 4-ج — مصدر سعر الفوترة `BillRate`**
  > - (أ) لكل مهمة (`Task.BillRate`). ← **موصى به** كبداية (بسيط وواضح).
  > - (ب) عقد/سعر لكل عميل. (ج) سعر لكل موظف.
  > **التوصية:** (أ) مع إمكانية تجاوزه عند إنشاء الفاتورة؛ (ب)/(ج) توسعة مستقبلية.
  - **تجميع:** فاتورة واحدة تضمّ سطور عدة مهام لنفس العميل خلال فترة (اختيار المستخدم للفترة/المهام). بعد الفوترة تُوسم السطور `Invoiced` (منعًا للفوترة المزدوجة — مفتاح تعطيل مثل نمط `PosSyncLog`).

### 4-3 المرتبات
- الساعات تغذّي الأجر عبر **موديول المرتبات القائم** (لا حساب أجر جديد).
  > **نقطة حسم 4-د — كيف تدخل الساعات المرتب؟**
  > - (أ) **تقرير ساعات لكل موظف/فترة** يستخدمه HR يدويًّا في مسير الرواتب. ← **موصى به لـ TM-6** (أقل مخاطرة، لا يمسّ منطق المرتب).
  > - (ب) مكوّن أجر بالساعة/إضافي يُحقن في `Payslip` تلقائيًّا (على غرار `AttendanceRecord.WorkedHours`).
  > **التوصية:** ابدأ بـ (أ)؛ (ب) بعد اعتماد سياسة واضحة للأجر بالساعة، عبر منطق المرتبات القائم فقط.

## 5) المهام التلقائية (Auto-generated Tasks)

### آلية التوليد
> **نقطة حسم 5-أ — آلية التوليد**
> - (أ) **أحداث دومين (Domain Events)** — لا يوجد ناقل أحداث في المشروع؛ بناؤه ثقيل ويلمس خدمات كثيرة.
> - (ب) **خدمة خلفية دورية تفحص (BackgroundService)** — **سابقة جاهزة**: `CrmReminderHostedService` + `IntegrityCheckHostedService`. ← **موصى به.**
> - (ج) خطّافات مضمّنة داخل الخدمات القائمة (تعديل كل خدمة).
> **التوصية:** **(ب) `TaskGeneratorHostedService`** دوري (كل X دقيقة، قابل للضبط) يشغّل «قواعد توليد» — يطابق نمط الكود، بلا لمس الخدمات القائمة. + **مفتاح منع ازدواج** (`AutoRuleKey` فريد لكل قاعدة+سجل) على غرار `PosSyncLog.LocalGuid` حتى لا تتكرر المهمة كل دورة.

### قواعد الإطلاق
| الحدث/الشرط | استعلام المصدر | المهمة المولّدة | مفتاح المنع |
|---|---|---|---|
| نقص مخزون (تحت حد الطلب) | أصناف رصيدها < ReorderPoint | «اطلب صنفًا» ← `Item` | `lowstock:{itemId}` |
| فاتورة متأخرة | ذمم عميل تجاوزت الاستحقاق | «حصّل فاتورة» ← `SalesInvoice` | `overdue:{invoiceId}` |
| أمر تشغيل اكتمل | `ManufWorkOrder.Status=Completed` بلا مراجعة | «راجع جودة» ← `ManufWorkOrder` | `qc:{woId}` |
| طلب توصيل جاهز | `PosOrder` توصيل حالته جاهز | «وصّل الطلب» ← `PosOrder` | `deliver:{orderId}` |
| موظف جديد | `Employee` أُنشئ حديثًا | «جهّز أوراق موظف» ← `Employee` | `onboard:{empId}` |

- كل قاعدة: **قابلة للتفعيل/الإيقاف** + **إسناد افتراضي** (مسؤول/دور) + إعادة استخدام المُحلِّل للربط.
- التوليد **مُعطَّل الازدواج**: لو المهمة (بنفس المفتاح) موجودة ومفتوحة، لا تُنشأ ثانية.

## 6) الأدوار والصلاحيات

`TaskUserRole { ID, CompanyId, EmployeeId, Role }` — **نفس نمط** `CrmUserRole`/`InventoryUserRole` (بالـ EmployeeId).

| الدور | يرى | يفعل |
|---|---|---|
| **الموظف** `TaskEmployee` | مهامه هو + وقته | ينفّذ، يسجّل وقتًا، يعلّق، ينهي |
| **المدير** `TaskManager` | مهام فريقه/فرعه | يوزّع، يعيد الإسناد، يراجع، يفتح المنتهية |
| **HR/محاسبة** `TaskFinance` | كل المهام والوقت | تكلفة/فوترة/مرتبات/تقارير + توليد فاتورة |

> **نقطة حسم 6-أ:** دور مستقل أم إعادة استخدام أدوار قائمة؟
> **التوصية:** جدول `TaskUserRole` مستقل بنفس النمط (اتساق + استقلال الموديول)، مع بوابة صلاحية مثل بقية الموديولات (`ITaskAccessService`).

## 7) التقارير

| التقرير | المصدر | لمن |
|---|---|---|
| مهامي / مهام الفريق | Task حسب المسؤول/الفريق + الحالة | الموظف/المدير |
| المهام المتأخرة | Task حيث `DueDate<الآن && ≠Done` | المدير |
| إنتاجية موظف | Σ ساعات + مهام منجزة/موظف/فترة | المدير/HR |
| تكلفة مشروع | Σ (ساعات × تكلفة الساعة) حسب `ProjectId` | HR/محاسبة |
| تكلفة أمر تشغيل | ساعات المهام المربوطة بالأمر × التكلفة (أو من سطور عمالة الأمر) | تصنيع/محاسبة |
| ساعات قابلة للفوترة/عميل | Σ ساعات Billable غير المفوترة/عميل | محاسبة |
| ملخّص مرتبات | ساعات/موظف/فترة | HR |

- كل التقارير **قراءة فقط**، بتصميم Metronic الموحّد (زي تقارير المشروع/المخزون القائمة)، مع فلاتر وبحث حقيقي.

| 3-ب | قابل للفوترة | مهمة / سطر | **سطر (يرث من المهمة)** |

| 4-ب | أثر التكلفة | تقريري / WO-labor / GL مشروع | **تقريري + WO عبر ManufService** |
| 4-ج | سعر الفوترة | مهمة / عميل / موظف | **مهمة (قابل للتجاوز)** |
| 4-د | المرتبات | تقرير / مكوّن أجر | **تقرير أولًا** |
| 5-أ | التوليد التلقائي | أحداث / خدمة دورية / خطّافات | **خدمة دورية + مفتاح منع ازدواج** |
| 6-أ | الأدوار | جديد / قائم | **`TaskUserRole` مستقل بنفس النمط** |

## 9) التقسيم المرحلي (كل مرحلة: تُبنى → تُختبر [dev test + inv=0] → وقفة)

| المرحلة | النطاق | اختبار القبول |
|---|---|---|
| **TM-1** | كيان `Task` + الشاشة (CRUD يدوي، بلا ربط) + الحالة/الأولوية + مرفقات/تعليقات + بوابة أدوار مبدئية | `tasks-test`: إنشاء/تعديل/إنهاء مهمة، الحالة تتحرّك صح، **بلا أي قيد محاسبي**، inv=0 |
| **TM-2** | الربط polymorphic (`EntityType`+`EntityId`) + المُحلِّل + الروابط العميقة لكل نوع | فتح مهمة مربوطة بفاتورة/عميل/أمر/طلب/موظف → الرابط يفتح السجل الصحيح؛ سجل محذوف يُعرض بأمان |
| **TM-3** | التايم شيت: مؤقّت حيّ (ابدأ/قف، خادم) + إدخال يدوي؛ `ActualHours=Σ` | `timesheet-test`: بدء/إيقاف يحسب الساعات، بدء ثانٍ يوقف الأول، Σ صحيح، inv=0 |
| **TM-4** | التكلفة: `IEmployeeCostService` + تكلفة تقريرية + (اختياري) سطر عمالة WO عبر `ManufService` | `task-cost-test`: التكلفة=ساعات×سعر الساعة؛ مهمة WO تُنشئ سطر عمالة عبر الكاتب القائم؛ inv=0 |
| **TM-5** | الفوترة: ساعات Billable → فاتورة بالساعة عبر `ReceivableService` + وسم Invoiced | `task-bill-test`: فاتورة خدمات (إيراد+ضريبة+ذمم، بلا مخزون)، لا فوترة مزدوجة، AR متّزن، inv=0 |
| **TM-6** | المرتبات: تقرير ساعات/موظف/فترة (يغذّي المرتب القائم يدويًّا) | `task-payroll-test`: التقرير يطابق Σ الساعات؛ لا كاتب أجر جديد؛ inv=0 |
| **TM-7** | المهام التلقائية: `TaskGeneratorHostedService` + القواعد + منع الازدواج + تفعيل/إيقاف كل قاعدة | `task-auto-test`: كل قاعدة تولّد مهمتها مرة واحدة؛ إعادة التشغيل لا تكرّر؛ inv=0 |
| **TM-8** | التقارير السبعة بتصميم Metronic موحّد + فلاتر/بحث | مراجعة بصرية + صحة الأرقام مقابل البيانات؛ inv=0 |

## 10) المخاطر والمحاذير
- **الفوترة المزدوجة:** يُمنع بوسم `Invoiced` على السطر + التحقق قبل الإنشاء (نمط `PosSyncLog`).
- **ازدواج الوقت:** مؤقّت واحد نشط/موظف؛ بدء جديد يوقف السابق.
- **ازدواج المهام التلقائية:** مفتاح `AutoRuleKey` فريد لكل (قاعدة+سجل).
- **حذف السجل المرتبط:** المُحلِّل يعرض «سجل محذوف» بدل رابط مكسور (لا FK قاعدة بيانات).
- **الثوابت:** لا شيء في TM-1..TM-3 يمسّ GL/المخزون؛ TM-4/TM-5 عبر كتّاب قائمين فقط؛ `inv-test-integrity=0` شرط إنهاء كل مرحلة.
- **الأداء:** فهارس على `Task(AssigneeEmployeeId, Status)` و`TimesheetEntry(TaskId)` و`(EmployeeId, Date)`.

## 11) خلاصة
موديول تشغيلي يبني فوق الموجود بالكامل: الموظف (مسؤول+تكلفة+مرتب) · بُعد المشروع (تكلفة) · `ReceivableService` (فوترة) · `ManufService` (عمالة WO) · نمط الربط polymorphic والخدمات الدورية (من CRM/السلامة). لا كاتب محاسبة جديد، والثوابت تبقى سليمة.

**بعد اعتمادك لنقاط الحسم نبدأ TM-1 (المهمة + الشاشة، يدوي، بلا ربط) ثم وقفة.**
