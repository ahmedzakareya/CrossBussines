# CrossBuy — المشاريع والمقاولات — P5: التكاليف الفعلية (مواد + عمالة) — تصميم فقط

> **الحالة:** تصميم بانتظار مراجعتك. **لا كود بعد.** يبني فوق: `StockService` (الكاتب الوحيد للمخزون) · التايم شيت TM-3 + `IEmployeeCostService` (سعر الساعة) · TM-2 ربط المهمة بالمشروع (`EntityType="Project"`) · بُعد `ProjectId` على القيود · `ProfitabilityAsync`.

---

## 1. النطاق والمبادئ

- **الهدف:** تسجيل **التكلفة الفعلية** للمشروع (صرف مواد + عمالة) موسومة بـ `ProjectId`، فتكتمل الربحية = الإيراد (مستخلصات 4102) − التكلفة الفعلية (5xxx).
- **أي قيمة مالية عبر الخدمات القائمة فقط:** المخزون عبر `StockService`؛ القيود عبر `JournalEntryService`. **لا كاتب جديد.**
- تكاليف BOQ (P1) تبقى **تقديرية** فقط؛ P5 هو التكلفة **الفعلية** (المقارنة estimate-vs-actual = مرحلة موازنة لاحقة).
- **`inv-test-integrity = 0`** — وبالأخص `stock_gl` (قيمة المخزون == حساب المخزون) و`tb_balanced`.
- **تقسيم مقترح:** **P5-أ (المواد)** ثم **P5-ب (العمالة)** — مستقلّان.

---

## 2. P5-أ — صرف المواد للمشروع

**الآلية:** أذن صرف مواد للمشروع (من مخزن) → لكل سطر حركة `StockService` (Direction −1) موسومة `ProjectId` → **Dr تكلفة تنفيذ المشروع (5xxx) / Cr المخزون** (بتكلفة الصنف الفعلية FIFO/متوسط). المخزون يقلّ فعليًّا (subledger + GL معًا عبر StockService، فـ`stock_gl` يبقى سليمًا).

**تدفّق:** مستند `ProjectMaterialIssue` (رأس: ProjectId, رقم, تاريخ, مخزن, حالة Draft/Posted) + `ProjectMaterialIssueLine` (ItemId, Qty, **BoqItemId اختياري**, لقطة تكلفة). عند الترحيل → `StockService.PostMovementAsync` لكل سطر (`SourceType="ProjectIssue"`, `ProjectId`, PostToGl=true).

---

## 3. P5-ب — عمالة المشروع

**الآلية:** المهام المربوطة بالمشروع (`TaskItem.EntityType="Project"`, `EntityId=projectId`) تُجمَّع ساعاتها من التايم شيت (TM-3) لكل موظف → التكلفة = Σ(ساعات × سعر الساعة من `IEmployeeCostService.HourlyCostAsync`) → ترحيل عبر `JournalEntryService`: **Dr تكلفة تنفيذ المشروع (5xxx) [موسوم ProjectId] / Cr 520101 عمالة [غير موسوم]** — إعادة تصنيف الراتب الفعلي إلى تكلفة المشروع (نفس منطق عمالة الموظف في التصنيع التي تُدين WIP وتُدائن 520101، لكن هنا الوعاء = ProjectId بدل WIP).

**حارس منع التكرار:** نعيد استخدام **`TaskItem.LaborPostedAt`** الموجود (يمنع ترحيل عمالة نفس المهمة مرتين) — نفس نمط TM-4.

**⚠️ توسيم الطرف الدائن:** الـ**Cr 520101 يُترك غير موسوم بـ ProjectId** عمدًا؛ وإلا (لو موسوم) يُلغي المدين في `ProfitabilityAsync` فتصبح تكلفة المشروع صفرًا. فيُحتسب المدين (5xxx الموسوم) فقط كتكلفة للمشروع، والصافي على مستوى الشركة = 0 (إعادة تصنيف).

---

## 4. مقاولو الباطن / المعدات

**✅ التوصية: تأجيل إلى P6** (كما ملت أنت). نبدأ بالمواد + العمالة (الأبسط والأهم). لاحقًا: الباطن = فاتورة مورد عبر `PayableService` موسومة ProjectId؛ المعدات = تحميل إهلاك/إيجار موسوم ProjectId.

---

## 5. الربط بالربحية (بلا تغيير في ProfitabilityAsync)

`ProfitabilityAsync` القائمة تحسب: **التكلفة = صافي مدين حسابات 5xxx للقيود الموسومة بالمشروع**. فبمجرد أن يُرحّل صرف المواد وعمالة المشروع إلى **5xxx موسوم ProjectId**، تدخل تلقائيًّا: **الربح = الإيراد (4102 موسوم) − التكلفة الفعلية (5xxx موسوم)**. لا تعديل على الدالة.
> شرط الصحّة: الطرف الدائن للعمالة (520101) والمخزون (1xxx) **غير موسومَين بالمشروع** (لا يُلغيان المدين). محقّق في التصميم أعلاه.

---

## 6. نقاط الحسم (خيارات + توصية)

### 6-1 حساب تكلفة التنفيذ (5xxx)
| الخيار | الوصف | العيب |
|---|---|---|
| أ) **حساب مخصّص جديد «تكلفة تنفيذ مشاريع» 5xxx (مثل 4102)** — موصى به | تحت 52؛ يُرحَّل عليه صرف المواد + العمالة، موسومًا ProjectId | يحتاج **توسيعًا صغيرًا في StockService** (تمرير حساب مدين مخصّص عند الصرف) |
| ب) إعادة استخدام COGS فئة الصنف | لا توسيع؛ الصرف يُدين COGS الفئة القائم | تكلفة المقاولات تختلط بتكلفة المبيعات في نفس الحساب (تفصلها فقط الـ ProjectId) |

**✅ التوصية: (أ) حساب مخصّص واحد «تكلفة تنفيذ مشاريع» (5xxx)** — يطابق هوية الموديول (4102/2104/1104) ويعطي تقارير نظيفة. الثمن = **توسيع `StockService.MovementRequest` ببارامتر اختياري `CounterAccountOverride`** (يغيّر الحساب المدين للصرف فقط؛ **المخزون يظل يُدائن بنفس القيمة فلا يمسّ `stock_gl`**؛ null = السلوك الحالي — ليس كاتبًا جديدًا، نفس نمط توسيع `CreateReceiptAsync` في P4). (اختياري: فصله لولدين 5201 مواد / 5202 عمالة لمقارنة BOQ لاحقًا — أميل لحساب واحد الآن.)

### 6-2 ربط الصرف بالمشروع/بند BOQ
**✅ التوصية:** `ProjectId` **إلزامي** على أذن الصرف (يُمرَّر لحركة StockService). **`BoqItemId` اختياري** لكل سطر (لمقارنة الفعلي بتقدير بند BOQ لاحقًا) — يُخزَّن على سطر الأذن، **لا يُخزَّن على `StockMovement`** (لا نمسّ جدول المخزون الأساسي). أذن الصرف مستند مستقل (رأس + سطور) مثل أذون المخزون القائمة.

### 6-3 آلية ترحيل العمالة
| الخيار | الوصف |
|---|---|
| أ) **زر ترحيل يدوي للمراجعة (مثل TM-4)** — موصى به | شاشة تعرض مهام المشروع + ساعاتها × السعر = التكلفة، وزر «ترحيل» (post-once عبر `LaborPostedAt`) |
| ب) ترحيل تلقائي | يرحّل فور تسجيل الساعات — بلا مراجعة (مرفوض: العمالة حسّاسة وتحتاج اعتماد) |

**✅ التوصية: (أ)** — مراجعة يدوية قبل الترحيل، post-once لكل مهمة. الطرف الدائن = **Cr 520101** (إعادة تصنيف الراتب، غير موسوم) — مطابق لعمالة الموظف في التصنيع. (بديل: حساب مقابل مخصّص «عمالة محمّلة على المشاريع» — أميل لإعادة استخدام 520101 للبساطة والاتساق.)

## 7. الشاشتان (بانتظار تصميمك — لا أجتهد)

- **(أ) صرف مواد للمشروع** — نقطة دخول: زر على صف المشروع (مثل BOQ/الإنجاز/المستخلصات). محرّر أسطر (اختيار المشروع + المخزن + أصناف/كميات + بند BOQ اختياري) → ترحيل. **أي نمط؟** جدول بنود Metronic (فاتورة) / بطاقة لكل سطر (زي BOQ الجديد) / نمط أذون المخزون القائمة؟
- **(ب) ترحيل عمالة المشروع** — شاشة لكل مشروع تعرض المهام المربوطة + ساعات × سعر = تكلفة + زر «ترحيل» (post-once). **أي نمط؟** قائمة حسابات + زر تأكيد (نمط الاعتماد الموجود)؟

**سؤالي:** أطبّق **الحساب المخصّص + توسيع StockService بـ `CounterAccountOverride`** (توصية 6-1)؟ وأي نمط للشاشتين؟

## 8. اختبار DevSeed المخطّط: `/api/dev/p5-test`

مشروع + مخزون صنف بتكلفة → **صرف مواد للمشروع** (Dr 5xxx تكلفة / Cr مخزون، موسوم ProjectId؛ المخزون قلّ) + **عمالة** (مهمة مربوطة بالمشروع + ساعات → Dr 5xxx / Cr 520101، موسوم ProjectId على المدين فقط) → يتحقّق:
- الصرف: Dr حساب التكلفة = تكلفة الصنف · Cr المخزون · موسوم ProjectId · رصيد المخزون نقص.
- العمالة: Dr التكلفة = ساعات×سعر · Cr 520101 (غير موسوم) · متوازن.
- **`ProfitabilityAsync`** للمشروع: التكلفة = (مواد + عمالة)، والربح = الإيراد − التكلفة.
- **`stock_gl` + `tb_balanced` + كل الفحوص = OK · inv=0**. ينظّف نفسه.
