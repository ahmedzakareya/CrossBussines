# Stage-TC-R3 — Event Model and Notification Flow

Full event catalog (20 proposed events): `Stage-TC-Catalogs-Appendix.md` §3 and `tasks-calendar-event-catalog.csv`.

---

## 1. Where the two modules stand today

| | Tasks | Calendar |
|---|---|---|
| Business events raised | **none** | **none** |
| Notifications raised | **none at all** | invite only, direct from `CalendarController.cs:104` |

So a task assigned to you today notifies you never; a task that becomes overdue tells nobody; a meeting moved from
Tuesday to Thursday informs no attendee. That is the state R3 is written against.

## 2. Why this phase PROPOSES events rather than raising them

The kernel's contract is mandatory and unforgiving: `IBusinessEventService.RecordAsync` must be called **inside the
caller's ambient transaction, immediately before commit, with no swallowing catch** — and it *throws* when there is
no ambient transaction. Raising an event therefore makes the event kernel a **hard runtime dependency** of the
raising path.

Applied here that means: the moment `TaskService.SaveAsync` raises `Task.Created`, a missing or changed
`BusinessEvents` table stops people creating tasks. A task with no timeline entry is a much smaller problem than a
task that cannot be created.

Two further preconditions are outside this tab:

1. **The entity codes do not exist yet.** An event name is validated against the registry, and neither `Task` nor
   `CalendarEvent` is registered (TC-G-01). An event cannot be raised for an unregistered entity.
2. **Onboarding is the third tab's call**, since it is their timeline and their notification projection that consume
   the result.

**So R3 delivers the model, the payloads, the ordering and the notification routing — and raises nothing.**

## 3. The event model

### 3.1 Naming and shape

`<EntityCode>.<Action>`, action PascalCase, validated against the registry. Every event carries `CompanyID` and the
aggregate id; `DedupKey` is set on every event whose producing action can be retried.

Two entity codes are requested (R4 §2): **`Task`** and **`CalendarEvent`**.

### 3.2 Task events (12)

Lifecycle: `Task.Created` · `Task.Assigned` · `Task.Reassigned` · `Task.StatusChanged` · `Task.Completed` ·
`Task.Reopened`
Time-driven: `Task.DueSoon` · `Task.Overdue`
Automation: `Task.AutoGenerated` (TM-7) · `Task.LinkMatched` (TM-9-ب) · `Task.LinkSuggested` (TM-9-ج)
Effort: `Task.TimeLogged` (TM-3)

`Task.AutoGenerated`, `Task.LinkMatched` and `Task.LinkSuggested` are the ones worth noticing: those transitions
already happen today **in background workers, silently**. They are the highest-value events in the set because they
are the ones a human currently has no way of learning about.

### 3.3 Calendar events (7)

`CalendarEvent.Created` · `.Updated` · `.Rescheduled` · `.Cancelled` · `.AttendeeInvited` · `.AttendeeResponded` ·
`.ReminderDue`

**`.Rescheduled` is deliberately separate from `.Updated`.** Changing a title and moving a meeting three days are
not the same fact: one is worth a notification to every attendee and the other is not. Collapsing them is how
notification fatigue starts.

`.AttendeeResponded` depends on an attendee response status, which does not exist yet and cannot be added until the
delete-and-reinsert behaviour is fixed (TC-G-08, R5 §4).

### 3.4 The link event

`TaskCalendarLink.Created` — raised on the `Task` aggregate when a task and a calendar event become associated. It
exists so the association is itself auditable rather than being inferred from two rows.

### 3.5 Sensitive fields

Task events carry `billRate` and timesheet `costRate` as **sensitive**: a timeline is read by more people than a
billing screen. `Task.Completed` and `Task.TimeLogged` must withhold them from a general timeline projection.

## 4. Notification flow

### 4.1 The two-stage rule

ADR-006 retains **direct producers** for entities that are not onboarded, and requires the **projection** once they
are. That gives a clean two-stage plan:

**Stage 1 — before onboarding (available immediately, no kernel dependency):**

```
TaskService / CalendarService  ──►  INotificationService.NotifyAsync(entityType, entityId)
```

Direct, in-process, no event, no outbox. This is a legitimate pattern today — it is exactly what Calendar's invite
already does — and it closes TC-G-04 and TC-G-05 without waiting for anyone.

**Stage 2 — after onboarding:**

```
service ──► RecordAsync (in-tx) ──► outbox ──► dispatch worker
                                        └──► BusinessEventNotificationMapper (pure)
                                              └──► NotificationProjectionConsumer ──► NotifyAsync (post-commit)
```

**The migration rule that must not be missed:** when an entity moves to Stage 2, its direct `NotifyAsync` calls must
be **removed in the same change**. Leaving both produces double notifications — the exact failure ADR-006 records as
the reason the inline `NotifyRoleAsync` was deleted when its projection landed.

### 4.2 Routing — who is notified, for what

| Event | Recipient | Rationale |
|---|---|---|
| `Task.Assigned` / `.Reassigned` | new assignee (and previous, on reassign) | the single most-missed notification today |
| `Task.Completed` | creator | the person who asked for it |
| `Task.Reopened` | assignee | work has come back |
| `Task.DueSoon` | assignee | default 24h before; per-company |
| `Task.Overdue` | assignee **and** supervisor | escalation is the point |
| `Task.AutoGenerated` | default assignee, else the supervisor | a rule-created task with no recipient is invisible |
| `Task.LinkMatched` | assignee | the movement they were waiting for has arrived |
| `Task.LinkSuggested` | supervisor | a decision is required (TM-9-ج) |
| `Task.StatusChanged`, `.TimeLogged`, `.Created` | **nobody** — timeline only | notifying on every status change is how people stop reading notifications |
| `CalendarEvent.AttendeeInvited` | attendee | already implemented |
| `CalendarEvent.Rescheduled` / `.Cancelled` | all attendees | the two that matter |
| `CalendarEvent.Updated` | **nobody** unless the change is material | see §3.3 |
| `CalendarEvent.AttendeeResponded` | organiser | |
| `CalendarEvent.ReminderDue` | attendees | per-attendee lead time |

**Deliberately silent** events still produce a **timeline** entry. The distinction between "worth interrupting
someone" and "worth recording" is the whole design here.

### 4.3 Time-driven events need a producer that does not exist

`Task.DueSoon`, `Task.Overdue` and `CalendarEvent.ReminderDue` are **not** produced by a user action, so no request
path can raise them. They need a scheduled producer.

Two workers already exist and already run on a timer — `TaskGeneratorHostedService` and
`TaskScheduleMatchHostedService` (`Program.cs:388-389`). The recommendation is a **third, separate worker** rather
than adding to either:

- both existing workers are `BackgroundService` with `IServiceScopeFactory` (correct pattern, keep it);
- a reminder sweep has a different cadence and a different failure profile from rule generation;
- a bug in reminders must not stop TM-7 from generating tasks.

Its contract: bind an explicit company scope (`WorkerScope.ForCompany`), scan per company, and be **idempotent** —
a `DueSoon` notification must be sent once per task per threshold, not once per sweep. That needs a
`TaskNotificationLog` keyed `(TaskId, Kind)`, mirroring the `TaskAutoLog` duplicate-guard pattern TM-7 already uses.

### 4.4 What must not happen

- No notification from inside a transaction that has not committed. Stage 1 calls `NotifyAsync` **after** the save,
  never before.
- No notification loop: `Task.AutoGenerated` must not itself trigger a rule that creates another task.
- No per-row notification on bulk operations. A sweep that touches 400 overdue tasks must aggregate per recipient.
- No sensitive field in a notification body (§3.5).

## 5. Ordering and dependencies

```
TC-G-01 registry codes (Platform)          TC-G-08 attendee identity (R5)
        │                                          │
        ▼                                          ▼
R3 Stage 1 notifications  ──────────►  R3 Stage 2 events + projection
   (no dependency — do now)                 (needs registry + third-tab consumers)
                                                   │
                                                   ▼
                                          R4 timeline + workspace
```

**Stage 1 is unblocked.** It requires no kernel change, no registry entry and no other tab. It is the single
highest-value, lowest-risk change available in this whole increment, and R5 §6 lists it first.

## 6. What R3 does not do

No event is raised, no notification call is added, no worker is written, and no mapper or consumer is touched. The
consumers named in the catalog are **requests to the third tab**, not work items for this tab.
