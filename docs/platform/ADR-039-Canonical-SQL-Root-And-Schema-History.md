# ADR-039 — Canonical SQL root, and two registries for schema state

**Status:** Accepted (R1) · **Owner:** Integration Owner · **Area:** Deployment
**Supersedes in part:** ADR-012 (Deployment Manifest and Schema History)

---

## Context

The repository has **two SQL deployment roots**:

| Root | Contents |
|---|---|
| `deploy/sql` | 57 slices, the generated `fresh/` build, operational backup and purge scripts, the server README |
| `CrossBuy/deploy/sql` | 60 slices, plus `manifest.json` |

**Four filenames exist in both. All four differ. None is byte-identical.** The manifest states the consequence itself: *"the same file name in two trees with different content, so `apply <name>.sql` is ambiguous."*

Three further facts shaped this decision, and two of them were not visible in earlier assessments:

1. **The authored side is already instrumented.** `CrossBuy/deploy/sql/manifest.json`, generated by `scan-sql-manifest.ps1`, registers **115 scripts** with SHA-256, an apply `rank`, the idempotency guards actually found in the text, and a verdict: `guarded` (92), `guarded-by-predicate` (7), `review` (1), `not-deployable` (1), `no-mutation` (14), `excluded` (3).
2. **The applied side is not instrumented at all.** `platform_schema_history.sql` — the table designed to record what has run — **has never been applied**. The deployment tracker is itself untracked.
3. **Provisioning does not actually replay slices.** `deploy/README.md` states the authoritative method is **BACKUP/RESTORE of `CrossBuyDB2`**, because EF migrations are broken and roughly 90 ad-hoc scripts in `C:/temp` built the schema and "cannot be safely or verifiably linearized". That is a third source of truth, outside the repository.

## Decision

### 1 — `CrossBuy/deploy/sql` is the canonical **authored** root

The governance tooling (`scan-sql-manifest.ps1`, `report-schema-history.ps1`) and `manifest.json` already live at `CrossBuy/deploy/`, and all newer platform work was authored there.

`deploy/` is **retained and re-labelled the deployment package root**: generated artifacts (`fresh/`, produced by `gen_fresh_db.ps1`), operational scripts, the server README. **It is not an authoring root.**

The 53 module slices still in the package root are a **migration backlog**, executed slice by slice with hash verification. They are listed, not failed — a gate that fails on day one for 53 historical files gets switched off, and a switched-off gate protects nothing.

### 2 — Two registries, and neither replaces the other

| Registry | Answers | Where |
|---|---|---|
| **Authored** | What slices exist, in what order, with what hash and idempotency verdict | `CrossBuy/deploy/sql/manifest.json` |
| **Applied** | What actually ran against *this* database, with what hash, when, by whom, and whether it succeeded | `dbo.PlatformSchemaHistory` |

The manifest cannot know what a database contains. The database cannot know what the repository intends. **Drift is the disagreement between them**, and it is only expressible if both exist.

### 3 — Governance extends the manifest; it does not replace it

`validate-sql-governance.ps1` adds only what a database-side report cannot see (G1–G7). The applied-side states — applied / changed / failed / pending / missing — remain with `report-schema-history.ps1` and are **not duplicated**. Building a second registry would recreate precisely the defect the two SQL trees demonstrate.

### 4 — Everything blocks; nothing warns

Divergent duplicates, `review`, `not-deployable`, duplicate `SliceId`, a stale manifest and a dangling registry entry all **block**. A warning in a deployment pipeline is a message nobody reads at 2 a.m. This matches the existing precedent that the bootstrap policy slice's drift detection *throws* rather than logging.

## Consequences

**Positive.** "Which slices are applied here?" becomes answerable. A slice edited after being applied is detectable — a name-only log can never produce that finding. Ambiguous applies are refused rather than guessed.

**Negative.** The pipeline is blocked today by a real backlog: 4 divergent pairs, 1 unreviewed script, 1 not-deployable script. That is the honest state, not a tooling defect.

**The bootstrap exception.** The applied registry cannot be established while the backlog blocks every run — a genuine ordering problem. `-Bootstrap` applies **only** `platform_schema_history.sql`, and only if that script is itself clean. It grants no relief to any other slice.

**Production is out of reach by construction.** `apply-sql-slices.ps1` refuses `CrossBuyDB`, `CrossBuyDB2` and `CrossBuy` under every flag combination. Production remains the runbook and a human. A deployment tool that can reach production by accident eventually will.

**Rollback is forward-only.** No down scripts. An applied slice is never edited — that is the "changed applied slice" drift case. Corrections are new slices with new `SliceId`s, mirroring the platform's *reverse, never delete* discipline.

## Verification performed

Against an isolated probe (`CrossBuyProbe_R1_Gov`, dropped afterwards; `CrossBuyDB2` never touched):

| Proof | Result |
|---|---|
| Production catalogue refusal, all three names, with `-Apply -Bootstrap` | **Refused, exit 2, nothing executed** |
| Governance block without `-Bootstrap` | **Blocked, exit 2, nothing executed** |
| `-Bootstrap` applies only the history table | 1 slice, exit 0 |
| Table, view, 2 indexes, 2 CHECK constraints created | All present |
| The apply recorded itself | Row with real SHA-256, `Success = 1` |
| Second apply is idempotent and **appends** | 2 rows, `ApplyCount = 2` |
| `CK_..._Hash` rejects a malformed hash | Rejected |
| `CK_..._Hash` rejects an **upper-case** hash | Rejected — the `BIN2` collation is load-bearing under a case-insensitive database |
| `CK_..._Error` rejects a failure with no reason | Rejected |
| `changed` drift detected after a hash mismatch | `CHANGED: 1`, exit 1 |

## Open

* The 4 divergent pairs and the 2 undeployable scripts require **their owners** to read and reconcile them (D-39). Governance detects them; it cannot decide what the schema should be.
* Reconciling the **restore-based provisioning path** with the slice path — deciding which is authoritative for a new environment — remains an owner decision.
* A restored database must be **stamped** into `PlatformSchemaHistory` before it can be promoted; an unstamped restore is an ungoverned database.
