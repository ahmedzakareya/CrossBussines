# CrossBuy — تصميم POS-9: طبقة العمل بلا اتصال (Offline)
**Offline-capable cashier — the last POS phase**

الحالة: **مسودّة تصميم للمراجعة** — لا كود بعد. بعد موافقة المستخدم نُقسّمها مراحل ونبنيها.

---

## 1) الهدف والمبدأ الحاكم
الكاشير يعمل **online عادةً** → يستمر في البيع لو **انقطع النت** → **يزامن فورًا** عند عودته. المتفق عليه من بداية المشروع:
- **عزل الترمينالات** (درج + ترقيم إيصال + وردية لكل ترمينال، POS-1) ⇒ الأرقام والنقد **لا تتعارض حتى offline** (كل ترمينال على جهاز واحد، تسلسله الخاص).
- **تعارض المخزون النادر عند المزامنة** ⇒ **تنبيه لا يمنع البيع**.
- **قاعدة صارمة: لا كاتب GL/مخزون على الجهاز.** لا محاسبة محلية إطلاقًا. الترحيل يحدث **على السيرفر عند المزامنة** عبر الخدمات القائمة (`ReceivableService`/`StockService`/`JournalEntryService`)، فتبقى **الثوابت مصدرها السيرفر**.

**البصيرة المعمارية المفتاحية:** الطلب المفتوح **صفر أثر محاسبي** (بالتصميم منذ RC-2) — كل دورة حياته (إنشاء/إضافة/كمية/حذف/إضافات/إرسال للمطبخ/طاولات) عمليات **تشغيلية بحتة**. المحاسبة تحدث **لحظة الدفع فقط**. لذا:
- **دورة الطلب المفتوح تعمل محليًا بالكامل offline** (لا تحتاج سيرفرًا — حالة تشغيلية).
- **الدفع** وحده يحتاج السيرفر للترحيل → offline: يُصفّى الطلب محليًا ويُوضع في **طابور مزامنة**؛ عند العودة يُعاد على السيرفر فيُرحّل عبر الخدمات القائمة.

الوضع الحالي (نُبني فوقه): لا PWA/service-worker؛ الكاشير SPA يرسل 41 نداء fetch للسيرفر لكل عملية؛ SignalR client محلي؛ ترقيم الإيصال = `PosTerminal.ReceiptPrefix + NextReceiptNo` (عدّاد لكل ترمينال) منفصل عن رقم الفاتورة المحاسبي (SV-yyyy).

## 2) التخزين المحلي (PWA + IndexedDB)

### نقطة الحسم 1 — ما الذي يُخزَّن محليًا
عند تحميل الترمينال (online)، تُسحب «حزمة بيانات الترمينال» وتُخزَّن في IndexedDB ليعمل الكاشير بلا نت:
- **الأصناف** (id/الاسم/NameEn/السعر/الضريبة/الصورة/QuickCode/الفئة) — من القائمة السريعة للفرع.
- **القائمة السريعة** (`PosMenuGroups` + `PosQuickItems`).
- **الإضافات** (`ModifierGroups`/`ModifierOptions` مع LinkedItem/QtyDeducted/ExtraPrice) — للـModal + الحساب.
- **`BranchItemSourcing`** (طريقة كل صنف + وصفة أصناف الطريقة-4 [BOM بالهالك]) — ليقرّر البيع السلوك offline.
- **`BranchPosSetting`** (مخزن البيع/نسبة الخدمة/العملة/رسوم التوصيل)، **القدرات** (Capabilities)، **معدّل الضريبة الافتراضي**.
- **الطاولات/الصالات** (floor: X/Y/W/H/الحالة) — للـDine-in offline.
- **طرق الدفع** (`BranchPaymentMethod`) + **ترويسة الإيصال** (هوية العلامة/اللوجو/الرقم الضريبي) + **الترمينال** (الدرج/البادئة/العدّاد).
- **الأصول الثابتة** (صور الأصناف/اللوجو) عبر **Cache API** في service-worker.

**نقطة الحسم 1أ — توقيت تحديث الكاش:**
- **الخيار أ (موصى):** تحديث تلقائي عند كل تحميل للترمينال **+ سحب دوري خفيف** أثناء الاتصال (مثلًا كل بضع دقائق) + زر «تحديث القائمة» يدوي. يضمن أحدث الأسعار/الإعداد قبل أي انقطاع.
- الخيار ب: تحديث يدوي فقط. أبسط لكنه يخاطر ببيانات قديمة offline.

**التوصية: الخيار أ.** الحزمة صغيرة (أصناف فرع واحد) والتحديث رخيص.

### نقطة الحسم 1ب — تقنية التخزين
- **الخيار أ (موصى):** **PWA** (manifest + service-worker) + **IndexedDB** للبيانات المهيكلة + **Cache API** للأصول. معيار قياسي، يعمل على أي متصفّح/جهاز لوحي، بلا تبعية خارجية (نبقى self-contained كبقية المشروع).
- الخيار ب: LocalStorage فقط — غير كافٍ (حدود الحجم + غير متزامن + لا فهارس).

**التوصية: الخيار أ (PWA + IndexedDB + Cache API).**

## 3) محرّك الطلب المحلي (offline)
دورة الطلب المفتوح تُنفَّذ محليًا في JS/IndexedDB — **مرآة لمنطق `PosOrderService` للطلب المفتوح** (لا محاسبة):
- التسعير من الكاش (سعر الصنف + الضريبة + نسبة الخدمة)، طيّ الإضافات في `UnitPrice` (RC-4b)، إعادة حساب الإجماليات (RecomputeAsync)، قراءة `BranchItemSourcing` (طريقة الصنف) للعرض.
- الطلبات المفتوحة/المعلّقة تُخزَّن في IndexedDB (**تصمد عبر إعادة التحميل** — لا تُفقد لو أُغلق المتصفّح أثناء الانقطاع).
- الطاولات/الإرسال-للمطبخ offline = علامات محلية (الطابعة الحرارية للتذاكر تعمل offline؛ KDS اللحظي online-only، قسم 7).

**تكرار المنطق:** جزء من منطق التسعير/الإضافات/الطرق سيُكرَّر في JS (لأن السيرفر غير متاح). هذا مقبول ومقصور على **الطلب المفتوح** (لا محاسبة)؛ الأرقام النهائية تُعاد التحقق منها على السيرفر عند الدفع/المزامنة (السيرفر هو الحَكَم).

---

## 4) طابور المزامنة (Sync Queue)

### نقطة الحسم 2 — حبيبات الطابور
- **الخيار أ (موصى): طابور الطلبات المُصفّاة (المدفوعة) فقط.** لأن العمليات المفتوحة بلا محاسبة، لا نطبّرها. عند الدفع offline يُسجَّل **إدخال واحد لكل طلب مدفوع** = لقطة كاملة: `{localGuid, terminalId, shiftId, orderType, tableId?, customerId?, lines[+modifiers], tip{amount,method}, الطريقة/التقسيم/الtenders, receiptNo المحلي, الوقت, أسعار offline}`. يُعاد **FIFO** بالترتيب عند العودة.
- الخيار ب: تطبير كل عملية (create/add/qty…). ثقيل بلا فائدة (الطلب المفتوح بلا محاسبة).

**التوصية: الخيار أ** — الطابور = الطلبات المدفوعة (نقطة المحاسبة الوحيدة). الطلبات المفتوحة/المعلّقة محلية فقط حتى تُدفع.

### نقطة الحسم 2أ — إعادة التشغيل (replay) + منع الازدواج
- كل إدخال يحمل **`localGuid`** (مفتاح id'potency). عند العودة، يُرسَل الطابور **تسلسليًّا** إلى نقطة سيرفر جديدة `POST /pos/sync/paid-order` التي: تُنشئ الطلب (مفتوح) + تضيف السطور/الإضافات + تستدعي **طريقة الدفع المطابقة القائمة** (`PayAsync`/`PayTendersAsync`/`PaySplitByItemAsync`) بالإكرامية → **السيرفر يرحّل GL/مخزون عبر الخدمات القائمة** (لا كاتب جديد).
- **idempotency:** جدول `PosSyncLog(localGuid)` — إدخال مُعاد إرساله (بعد نجاح سابق) **يُتجاهَل** فلا يُرحَّل مرتين. صفر ازدواج محاسبي.
- فشل جزئي: الإدخال الذي يفشل يبقى في الطابور (retry)؛ اللاحق لا يُرحَّل قبله (تسلسلي).

## 5) الترقيم offline
عزل الترمينال يضمن عدم التعارض. **العدّاد يصبح محليًّا offline:**
### نقطة الحسم 3 — سلطة العدّاد
- **الخيار أ (موصى): العدّاد المحلي هو المرجع للترمينال.** الترمينال يملك تسلسله (`ReceiptPrefix + عدّاد محلي في IndexedDB`)؛ لأن **جهازًا واحدًا فقط يشغّل الترمينال** (وردية واحدة مفتوحة لكل ترمينال — POS-1) فالبادئة+العدّاد **فريدان عالميًّا حتى offline**. عند المزامنة: الإيصال يحمل رقمه المحلي المُسبَق؛ السيرفر يضبط `PosTerminal.NextReceiptNo = max(المحلي)` فلا يتراجع.
- الخيار ب: حجز نطاق أرقام مسبقًا من السيرفر. تعقيد بلا داعٍ (البادئة تكفي للعزل).

**التوصية: الخيار أ.** ضمانة: **جلسة/جهاز واحد لكل ترمينال** (نفرضها — الوردية المفتوحة الواحدة تضمنها).
**تأكيد:** **رقم الفاتورة المحاسبي (SV-yyyy) يُسنِده السيرفر عند المزامنة** — منفصل عن رقم إيصال الترمينال (الفصل قائم منذ POS-1). فالعميل يأخذ رقم الإيصال المحلي offline، والفاتورة المحاسبية تُرقَّم عند الترحيل.

---

## 6) الترحيل المحاسبي عند المزامنة
- **offline: صفر GL/مخزون على الجهاز.** لا `StockService`/`JournalEntryService` محليًّا — غير موجودة أصلًا في المتصفّح.
- عند المزامنة، `POST /pos/sync/paid-order` يعيد بناء الطلب على السيرفر ويستدعي **طريقة الدفع القائمة** → الفاتورة + المخزون + GL تُرحَّل عبر `ReceivableService.CreateSalesInvoiceAsync` (+ COGS via StockService) + السند + قيد الإكرامية (RC-5) — **نفس المسارات المُثبَتة** (RC-2/POS-7/RC-4c/BIS-2/RC-5). **الثوابت الثمانية مصدرها السيرفر** كما هي.
- **تكلفة COGS عند الترحيل = التكلفة المتحرّكة الحالية على السيرفر** لحظة المزامنة (سعر البيع للعميل ثُبِّت offline؛ التكلفة تُحسب عند الترحيل) — طبيعي ومتّسق مع بقية النظام.

---

## 7) تعارض المخزون عند المزامنة — تنبيه لا يمنع

### نقطة الحسم 4 — الاكتشاف والعرض
- **الخيار أ (موصى): ترحيل غير-حاجز + تسجيل تعارض + شاشة مراجعة للمدير.** عند الـreplay، السيرفر **يرحّل البيع دائمًا** (يصرف المخزون ولو سالبًا حسب السياسة القائمة)، ثم **يفحص ويسجّل تعارضًا** إن: (أ) قاد الصرف المخزون سالبًا · (ب) الصنف أصبح غير نشط · (ج) اختلف السعر offline عن سعر السيرفر الحالي. التعارضات تُخزَّن (`PosSyncConflict{orderGuid, itemId, kind, offlineValue, serverValue}`) وتُعرض في **شاشة «مراجعة المزامنة» للمدير** + toast — **دون منع/تعليق البيع** (كما اتُّفق).
- الخيار ب: تعليق الطلب لموافقة المدير. **مرفوض** (يخالف الاتفاق: تنبيه لا يمنع).

**التوصية: الخيار أ.** البيع تمّ فعلًا للعميل offline؛ الترحيل يعكسه والمدير يُراجع الحالات النادرة لاحقًا.

## 8) ما يبقى online-only (لا يعمل offline)

### نقطة الحسم 5 — حدود الـoffline
- **يعمل offline:** بناء الطلب (فتح/إضافة/كمية/حذف/إضافات/طاولات/تعليق) · الطريقة-4 (backflush يُحسب على السيرفر عند المزامنة، لكن الطلب يُبنى offline) · الدفع (نقدي/بطاقة/تقسيم/إكرامية) بطابور · طباعة الإيصال الحراري (client-side أصلًا) · إغلاق الوردية (العدّ محلي، القيد يُطبَّر).
- **online-only (يتطلب النت):**
  - **إعداد الأدمن** (الترمينالات/القائمة/الإضافات/مصادر التوفير/الأدوار/مناطق التوصيل) — نادر، للأدمن.
  - **التقارير** المحاسبية (تقرأ من السيرفر). **تقرير Z**: نسخة **محلية مبدئية** من بيانات جهاز الوردية (يعرف مبيعاته/إكرامياته)؛ الـZ الرسمي (بالـGL) بعد المزامنة.
  - **KDS اللحظي/SignalR** — يتطلب الشبكة (جهاز مطبخ منفصل). offline: الإرسال-للمطبخ علامة محلية + تذكرة مطبوعة؛ لا بثّ لحظي.
  - **لوحة التوصيل · الحجوزات · مزامنة الطلبات المفتوحة بين الأجهزة/KDS** — تنسيق متعدد-الأجهزة يحتاج النت.
  - **الإلغاء/المرتجع لفاتورة مُرحَّلة** (RC-6c) — يتطلب `ReverseAsync` على السيرفر. **إلغاء طلب offline لم يُزامَن بعد = حذفه من الطابور** (لم يُرحَّل شيء)؛ إلغاء فاتورة مُزامَنة = online-only.
  - **الدخول/فتح وردية جديدة** — يحتاج السيرفر. offline **يواصل** الجلسة/الوردية المفتوحة (الـctx مُخزَّن)؛ لا دخول/فتح وردية جديدة offline.

**التوصية: كما أعلاه** — offline يغطّي البيع الكامل؛ التنسيق والمحاسبة والإعداد online.

## 9) الأثر على الثوابت
- **offline: صفر أثر** (لا GL/مخزون على الجهاز).
- **عند المزامنة:** الترحيل عبر الخدمات القائمة فقط → `inv-test-integrity=0` كما هو (الثوابت مصدرها السيرفر).
- نقطة السيرفر `/pos/sync/paid-order` **لا تكتب GL/مخزون مباشرةً** — تستدعي طرق الدفع القائمة (التي تستدعي الكاتبَين الوحيدَين). `PosSyncLog` يمنع الازدواج.

---

## 10) التقسيم المرحلي (كل مرحلة تُبنى وتُختبر وتقف)
- **POS-9a — قشرة PWA + الكاش:** manifest + service-worker + كشف online/offline + سحب «حزمة الترمينال» إلى IndexedDB + تخزين الأصول (Cache API). التحقّق: الترمينال **يُحمَّل ويعرض القائمة offline** (بعد تحميل أول online).
- **POS-9b — محرّك الطلب المحلي:** دورة الطلب المفتوح كاملة في IndexedDB (إضافة/كمية/حذف/إضافات/إجماليات/تعليق/طاولات) بالتسعير المكيَّش، تصمد عبر إعادة التحميل. التحقّق: بناء طلب دقيق offline (إجماليات = السيرفر).
- **POS-9c — الدفع offline + الطابور + الترقيم المحلي + الطباعة:** تصفية الطلب محليًا، رقم إيصال محلي، طباعة، إدخال في `syncQueue`. التحقّق: بيع offline كامل → إيصال مطبوع + إدخال في الطابور، بلا نت.
- **POS-9d — الترحيل عند المزامنة:** `POST /pos/sync/paid-order` + `PosSyncLog` (idempotency) → يستدعي طرق الدفع القائمة؛ مزامنة تلقائية عند العودة. **اختبار `pos-sync-test`:** طلب offline (نقدي + بطاقة + تقسيم + إكرامية + إضافات + صنف طريقة-4) يُعاد → فاتورة/مخزون/GL تُرحَّل صح، إعادة الإرسال تُتجاهَل (id'potency)، AR=0، TB متوازن، inv=0.
- **POS-9e — التعارض + المراجعة + إغلاق الوردية offline:** كشف تعارض المخزون (سالب/غير نشط/سعر) + شاشة مراجعة المدير (غير حاجزة) + تطبير إغلاق الوردية (القيد يُرحَّل عند المزامنة). التحقّق: بيع offline يقود مخزونًا سالبًا → يُرحَّل + يظهر تنبيه لا يمنع؛ inv=0.

**ترتيب:** 9a → 9b → 9c → 9d (القلب المحاسبي) → 9e. كل مرحلة: تصميم صغير عند اللزوم → بناء → تحقّق → وقفة.

## 11) أسئلة الحسم للمستخدم (قبل البناء)
1. تحديث الكاش: تلقائي عند التحميل + دوري + زر يدوي (موصى)؟
2. التخزين: PWA + IndexedDB + Cache API (موصى)؟
3. حبيبات الطابور: الطلبات المدفوعة فقط (موصى) أم كل عملية؟
4. الترقيم offline: العدّاد المحلي مرجع + جهاز واحد لكل ترمينال (موصى)؟
5. تعارض المخزون: ترحيل غير-حاجز + شاشة مراجعة (موصى) أم تعليق للموافقة؟
6. حدود offline (قسم 8): الإعداد/التقارير/KDS-اللحظي/الإلغاء-بعد-المزامنة online-only (موصى)؟
7. الطلبات المفتوحة offline: محلية فقط تصمد بإعادة التحميل (موصى)، ومزامنة الطلبات-المفتوحة بين الأجهزة مؤجّلة؟

**لا كود بعد — في انتظار قراراتك ثم نبدأ POS-9a.**
