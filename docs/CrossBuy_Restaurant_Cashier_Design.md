# CrossBuy — تصميم تنفيذي: كاشير المطعم (POS)

**النوع:** تصميم تنفيذي (لا كود) — يُحسم قبل البناء. **الحالة:** مسودة للمراجعة.
**التاريخ:** 2026-07 · **يُقرأ مع:** `CrossBuy_Platform_Restaurant_Design.md`، وذاكرة operations-platform.

> **مبني على القائم — لا منطق موازٍ:**
> - **التسعير:** `PricingService` (قوائم أسعار + عروض + عملة) — لا تسعير جديد.
> - **المخزون:** `StockService` الكاتب **الوحيد** (backflush الوصفة، `ProducePartial`/`Assemble`, `ProductionMethod`, `ItemComponent`/BOM).
> - **الفاتورة:** `ReceivableService.CreateSalesInvoiceAsync` (تُنشئ الإيراد + ض.ق.م + حركة COGS).
> - **GL:** `JournalEntryService` الكاتب **الوحيد**.
> - **الأساس المبني:** `BranchCapability`, `BranchPosSetting` (مخزن البيع/قائمة الأسعار/الخدمة%/العملة), `RestaurantTable.QrToken`, `DiningArea`, `Brand`.
> **الثابت الحاكم:** الطلب المفتوح = حالة تشغيلية بلا أثر محاسبي؛ كل الأثر المالي يقع **عند التسوية** عبر الخدمات القائمة → الثوابت الثمانية تبقى خضراء.

## القسم 1 — إعداد الكاشير (شغل أدمن، يقرأه الكاشير)

### 1.1 الأصناف السريعة (أزرار لمس)
**الكيان المقترح:** `PosQuickItem { ID, BranchId, ItemId, GroupId?, Sort, ColorHint?, IsActive }` — صف لكل زر في فرع.
- التبويبات (تجميع الأزرار): كيان خفيف `PosMenuGroup { ID, BranchId (or BrandId), Name, Sort }` يمثّل تبويبات الكاشير (مثل: مشروبات / ساندويتشات / حلويات).
- الأدمن يرتّب الأزرار داخل كل تبويب (Sort) لكل فرع.

**نقطة حسم 1.1 — مستوى التخزين:**
- **(موصى به) لكل فرع** (`PosQuickItem.BranchId`) — كل فرع يعرض أصنافه وترتيبه.
- بديل: على مستوى Brand يُورَّث للفروع — أبسط لكن أقل مرونة.

**نقطة حسم 1.1ب — مصدر التبويبات:**
- **(موصى به) `PosMenuGroup` مستقلّ** (تبويبات عرض للكاشير) منفصل عن فئات المحاسبة (`ItemCategory`) — الكاشير يُرتَّب تجاريًا لا محاسبيًا.
- بديل: إعادة استخدام `ItemCategory` كتبويبات — بلا كيان جديد لكن يخلط العرض بالمحاسبة.

### 1.2 الأكواد/الاختصارات السريعة (PLU)
ربط الصنف بكود رقمي قصير للإدخال بلوحة المفاتيح (اكتب الرقم + Enter → يُضاف الصنف).

**نقطة حسم 1.2 — أين يُخزَّن الكود:**
- **(موصى به) على الصنف نفسه** — حقل `Item.QuickCode` (nullable، فريد داخل الشركة). الـPLU خاصية للمنتج، وأبسط وأثبت، ويعمل في كل الفروع بلا تكرار.
- بديل: لكل فرع (`PosBranchItemCode`) — يسمح بأكواد مختلفة لكل فرع، لكن تعقيد أعلى. **مؤجَّل** ما لم يُطلب.
> يمكن أيضًا الاستفادة من `Item.Barcode`/`ItemBarcode` القائمة للمسح، والـQuickCode للإدخال اليدوي السريع.

### 1.3 البحث السريع
سلوك **مدمج، بلا إعداد أدمن**: اختصار (مثل `/` أو زر بحث) يفتح نافذة بحث فورية في كل الأصناف النشطة (تُستهلك خدمة البحث القائمة `ItemsSuggest`/`ItemPickData`). النتيجة تُضاف للطلب. يعمل بالكود/الاسم/الباركود.

## القسم 2 — الإضافات/الخيارات (Modifiers) — الأهم

**الفكرة:** مجموعات Modifier **قابلة لإعادة الاستخدام**، تُعرَّف مرّة وتُربط بأصناف كثيرة.

### الكيانات المقترحة
| الكيان | الحقول | الغرض |
|---|---|---|
| `ModifierGroup` | ID, CompanyId, Code, Name, **Type** (Choice/AddOn), MinSelect, MaxSelect, IsActive | تعريف المجموعة |
| `ModifierOption` | ID, GroupId, Name, **LinkedItemId** (صنف مخزني), **QtyDeducted**, **ExtraPrice**, Sort | خيار داخل المجموعة |
| `ItemModifierGroup` | ID, ItemId, GroupId, Sort, RequiredOverride? | ربط مجموعة↔صنف (many-to-many) |

**النوعان:**
- **Choice (بديل):** إجباري، `MinSelect=1, MaxSelect=1`، `ExtraPrice=0` (مثال: مشروب العرض — بيبسي/سفن/ميرندا).
- **AddOn (إضافة):** اختياري، `MinSelect=0, MaxSelect=N`، `ExtraPrice>0` (مثال: بطاطس/جبنة زيادة).

**كل خيار = ربط بصنف مخزني + كمية تُخصم + سعر إضافي:**
- `LinkedItemId` → الصنف الذي يُخصم من المخزون عند البيع (القسم 3).
- `QtyDeducted` → الكمية المخصومة (مثال: 1 علبة بيبسي، 50جم جبنة).
- `ExtraPrice` → يُضاف لسعر سطر الطلب (0 للبديل، رقم للإضافة) بعملة الفرع.

**نقطة حسم 2 — عام أم لكل صنف:**
- **(موصى به) مجموعة عامة قابلة لإعادة الاستخدام** تُربط بأصناف متعددة عبر `ItemModifierGroup` — «مشروب العرض» تُعرَّف مرة وتُربط بكل الوجبات.
- بديل: مجموعة لكل صنف — تكرار وصيانة أصعب.

**نقطة حسم 2ب — سعر الإضافة:**
- **(موصى به) `ExtraPrice` ثابت على الخيار** (يُضاف مباشرة للسطر) — بسيط ومباشر؛ سعر الطبق الأساسي يبقى عبر `PricingService`.
- بديل: تمرير الإضافات عبر `PricingService` — مرونة أعلى (عروض على الإضافات) لكن أعقد. مؤجَّل.

## القسم 3 — خصم المخزون الصحيح عند البيع (النقطة الحرجة — تجنّب الخصم المزدوج)

**القاعدة:** عند التسوية، سلوك خصم كل بند يُقرّر من `Item.IsComposite` + `Item.ProductionMethod` (والوصفة `ItemComponent`):

| نوع البند | القرار عند البيع |
|---|---|
| **صنف تام مُصنّع مسبقًا** (`IsComposite=Assembly` + `ProductionMethod=OrderBased`، صُنِع عبر أمر تشغيل ومكوّناته خُصمت وقت التصنيع ودخل التام للمخزون) | يُخصم **التام فقط** (حركة صرف للصنف التام) — **بلا** backflush للمكوّنات (وإلا خصم مزدوج) |
| **صنف يُجمَّع عند الطلب** (`ProductionMethod=Immediate` / وصفة تُفكّك عند البيع) | **backflush للمكوّنات** عند البيع (صرف مكوّنات الوصفة) — لا يُخصم «تام» لأنه لا يوجد تام مخزّن |
| **صنف مخزني بسيط** (`IsComposite=false`) | يُخصم **الصنف نفسه** بكميته |
| **خيار Modifier** (`ModifierOption.LinkedItemId`، صنف مخزني قائم لم يُصنّع) | يُخصم **الصنف المرتبط** بكمية `QtyDeducted` |

**كيف يقرّر الكاشير/التسوية:**
- لكل سطر: يقرأ الصنف → `IsComposite` + `ProductionMethod`:
  - `OrderBased` → طلب صرف تام (`MovementRequest` للصنف التام) عبر `StockService`.
  - `Immediate`/وصفة → استدعاء مسار الـbackflush القائم (`AssembleAsync`/تفكيك BOM) عبر `StockService`.
  - بسيط → صرف مباشر.
- لكل modifier مختار في السطر: طلب صرف للصنف المرتبط بكميته.
- **`StockService` يبقى الكاتب الوحيد** — الكاشير يمرّر طلبات الحركة فقط؛ COGS يُحسب بالخدمة (تام = تكلفة التام؛ backflush = مجموع تكاليف المكوّنات)، مع بُعد **Brand** (والمشروع اختياريًا).

**نقطة حسم 3 — صنف OrderBased بلا رصيد تام:**
- **(موصى به) البيع يتطلّب رصيد تام** (يُصنَّع مسبقًا عبر أمر تشغيل) → صرف تام؛ ولو لا رصيد → يُرفض/ينبّه (لا backflush تلقائي، منعًا للازدواج).
- بديل: backflush تلقائي عند غياب التام — يُدخل التباسًا وخطر ازدواج. مرفوض.

## القسم 4 — دورة الطلب (متعدّد الأدوار على أجهزة مختلفة، طلب مشترك واحد)

> **تحديث جوهري (2026-07):** النظام متعدّد الأدوار/الأجهزة تشترك في **نفس `PosOrder`**: الجرسون (تابلت) يفتح/يضيف/يرسل — لا يدفع؛ المطبخ (KDS) يحدّث الحالة فقط؛ الكاشير (مكتب) يحصّل ويقفل. **الترحيل عند الدفع فقط عبر الكاشير.**

**الكيانات (حالة تشغيلية خفيفة — بلا أثر محاسبي حتى «مدفوع»):**
- `PosOrder { ID, BranchId, BrandId, Type (DineIn/Takeaway/Delivery), TableId?, Status, WaiterEmployeeId?, CashierEmployeeId?, GuestCount, SubTotal/ServiceAmount/TaxTotal/GrandTotal, OpenedAt/ClosedAt, InvoiceId? }`
- `PosOrderLine { ID, OrderId, ItemId, Qty, UnitPrice, LineNotes, CourseNo, KdsStatus, StationId? }` — **حالة KDS على مستوى السطر** (تسمح بإرسالات إضافية بعد أول إرسال).
- `PosOrderLineModifier { ID, OrderLineId, ModifierOptionId, LinkedItemId, QtyDeducted, ExtraPrice }` (لقطة الخيار وقت الاختيار)

**آلة حالات الطلب (Order Status) — أي دور يحرّك أي انتقال:**
| الحالة | → التالية | مَن يحرّكها | الأثر المحاسبي |
|---|---|---|---|
| **مفتوح** (Open) | مُرسل للمطبخ | الجرسون (إضافة أصناف ثم «إرسال») | لا شيء |
| **مُرسل للمطبخ** (SentToKitchen) | جاري التحضير | المطبخ | لا شيء |
| **جاري التحضير** (Preparing) | جاهز | المطبخ | لا شيء |
| **جاهز** (Ready) | مُقدَّم | الجرسون (سلّم للطاولة) / التيك-أواي: تسلّم | لا شيء |
| **مُقدَّم** (Served) | **مدفوع** | **الكاشير (تحصيل)** | ✅ **هنا فقط**: فاتورة + خصم مخزون + GL |
| **مدفوع** (Paid) | مقفول | الكاشير (طباعة/إقفال) | (تمّ عند الدفع) |
| أي حالة قبل الدفع | ملغى (Void) | الكاشير/المدير (بصلاحية) | لا شيء (إلغاء تشغيلي) |

- **إضافة أصناف بعد الإرسال:** السطر الجديد يبدأ `KdsStatus=Pending` ويُرسل للمطبخ مستقلًّا؛ حالة الطلب الكلّية تبقى تشغيلية. لا شيء يرحّل.
- **الطلب يبقى بلا أثر محاسبي في كل الحالات حتى «مدفوع».**

**عند الدفع فقط (بيد الكاشير، ذرّيًا):**
1. تسعير كل سطر عبر **`PricingService`** (قائمة أسعار الفرع من `BranchPosSetting.DefaultPriceListId`) + إضافات الـmodifiers.
2. **الخدمة%** من `BranchPosSetting.ServiceChargePct` + الضريبة.
3. `PosOrder` → **فاتورة بيع** عبر `ReceivableService.CreateSalesInvoiceAsync` (من `BranchPosSetting.DefaultSalesWarehouseId`) → إيراد + ض.ق.م + AR/نقدية.
4. **خصم المخزون** حسب القسم 3 (عبر `StockService` — الكاتب الوحيد) → COGS + مخزون، ببُعد **Brand**.
5. القيد عبر `JournalEntryService` (الكاتب الوحيد للـGL).
- **StockService/JournalEntryService الكاتبان الوحيدان، والترحيل عند الدفع فقط → الثوابت الثمانية تبقى خضراء.**

**نقطة حسم 4 — لحظة خصم المخزون:** **(موصى به) عند الدفع (الكاشير) فقط** — حدث محاسبي واحد نظيف. إرسال المطبخ/التحضير تشغيلي بحت.
**نقطة حسم 4ب — ذرّية التسوية:** معاملة واحدة؛ فشل المخزون/GL → يبقى الطلب «مُقدَّم» (لا فاتورة جزئية). (موصى به.)
**نقطة حسم 4ج — حالة الطلب: كلّية أم لكل سطر؟** **(موصى به) الاثنان:** حالة كلّية للطلب + `KdsStatus` لكل سطر (يتيح إرسالات متتابعة وتتبّع المطبخ الدقيق).

## القسم 4-أ — الأدوار والأجهزة والتحديث اللحظي (real-time)

### الأدوار والصلاحيات (فوق نظام الصلاحيات القائم `AccPerm`/`InvPerm` + خدمات `CanAsync`)
| الدور | الجهاز/الشاشة | يستطيع | لا يستطيع |
|---|---|---|---|
| **الجرسون** `pos-waiter` | تابلت (الكاشير-touch بوضع جرسون) | فتح طاولة، إضافة أصناف/modifiers، إرسال للمطبخ، تعليم «مُقدَّم» | **لا يدفع**، لا يرحّل |
| **المطبخ** `pos-kitchen` | شاشة KDS | رؤية الطلبات، نقل السطر/الطلب: جاري التحضير → جاهز | لا يضيف، لا يدفع |
| **الكاشير** `pos-cashier` | مكتب | رؤية الطلب، **تحصيل → دفع** (الترحيل)، إقفال، إلغاء | (الأوسع) |
| **المدير** `pos-manager` (اختياري) | أي جهاز | كل ما سبق + إلغاء/خصم تجاوزي | — |

- تُضاف صلاحيات POS الجديدة (`pos-waiter/pos-kitchen/pos-cashier/pos-manager`) عبر **نفس نمط الصلاحيات القائم** (سمة على الأكشن + خدمة وصول)، وتُسنَد للموظفين كأي صلاحية حالية.
- **الحاجز الحاسم:** إجراء «الدفع/التسوية» (الوحيد المُرحِّل) محمي بـ`pos-cashier` فقط — الجرسون/المطبخ لا يصلونه.

### التحديث اللحظي (SignalR — يعيد استخدام البنية القائمة)
- **يُعاد استخدام SignalR القائم** (`Hubs/NotificationsHub.cs` + التسجيل في `Program.cs`). **نقطة حسم 4د:** **(موصى به) Hub مخصّص `PosHub` بمجموعات لكل فرع (branch group)** بجانب الـHub القائم — فصل نظيف لأحداث الكاشير؛ بديل: توسيع `NotificationsHub` (أبسط لكن يخلط الإشعارات بأحداث POS).
- **الأحداث:** `OrderSentToKitchen` · `LineStatusChanged` · `OrderReady` · `OrderPaid`. كل جهاز ينضمّ لمجموعة فرعه.
- **السلوك:** الجرسون يرسل → **المطبخ يرى فورًا**؛ المطبخ يعلّم «جاهز» → **الجرسون/شاشة الحالة ترى فورًا** — بلا refresh يدوي.

### شاشة المطبخ (KDS)
- تعرض الطلبات المفتوحة وحالاتها: رقم الطلب/الطاولة، الأصناف (+modifiers/ملاحظات)، وحالة كل سطر (Pending/Preparing/Ready). المطبخ يضغط لتحديث الحالة → يبثّ لحظيًا.
- **KDS جزء من دورة الطلب الأساسية** (الجرسون يرسل من البداية) — لا مرحلة متأخرة منفصلة (انظر إعادة ترتيب المراحل، القسم 6).

### شاشة حالة الطلب (اختياري — للتيك-أواي)
- عرض عام «رقم الطلب: جاري التحضير / جاهز للتسليم / تسلّم» — يُحدَّث لحظيًا عبر نفس الأحداث. بلا تسجيل دخول (شاشة عرض).

## القسم 5 — شكل الشاشة (RTL)

```
┌─────────────────────────── نوع الطلب: [صالة/طاولة] [تيك-أواي] [دليفري] ───────────────┐
│  الطلب الحالي (شمال)          │              الأصناف (يمين)                              │
│  ─ سطر: طبق + modifiers       │   [تبويبات: مشروبات · ساندويتش · حلويات]                │
│  ─ سطر: ...                   │   [أزرار لمس سريعة للأصناف]                             │
│  الإجمالي / الخدمة% / الضريبة  │   [بحث سريع «/» + إدخال كود PLU]                         │
├──────────────────────────────┴─────────────────────────────────────────────────────────┤
│  [إرسال للمطبخ]   [دفع]   [تقسيم الحساب]   [خصم]                                          │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```
- **المعمار:** هجين — صفحة **touch-first داخل CrossBuy** + endpoints JSON (add-line / add-modifier / send-kitchen / settle) — يعيد الجلسة والخدمات، مسار ترقية للأوفلاين لاحقًا.
- **يقرأ `BranchCapability`** ليعرض/يخفي: الطاولات + المطبخ + الإضافات (للمطعم)؛ الهايبر/التجزئة يخفي الطاولات ويُظهر الباركود/الوزن.
- يدعم: **لمس** (أزرار) + **أكواد** (PLU + باركود) + **بحث سريع**.
- **الأوفلاين:** online/LAN الآن، الأوفلاين الكامل مؤجَّل (يطابق وثيقة المنصة).

**نقطة حسم 5 — الكاشير كصفحة MVC أم SPA منفصلة:**
- **(موصى به) صفحة hybrid داخل MVC** الآن — أسرع بناءً وإعادة استخدام؛ SPA/أوفلاين لاحقًا.

## القسم 6 — تقسيم لمراحل البناء (كل مرحلة تُبنى وتُختبر وحدها)

أُعيد الترتيب بعد إدخال الأدوار + حالات الطلب + real-time + **KDS ضمن الأساس** (لا مرحلة متأخرة):

| المرحلة | المحتوى | الإثبات |
|---|---|---|
| **RC-1 — إعداد الكاشير** | `PosQuickItem`/`PosMenuGroup` + `Item.QuickCode` + شاشات الأدمن للترتيب | الأزرار/الأكواد تُحفظ وتُقرأ لكل فرع |
| **RC-2 — المسار الحرج (دفع بيد الكاشير)** ⭐ | `PosOrder`/Line + آلة الحالات (بلا تقسيم أدوار بعد) + تسوية الكاشير: **دفع** → فاتورة + خصم مخزون(ق3) + GL + Brand + تسعير + خدمة% | **أصغر مسار يثبت التكامل**: بيع طبق (تام/backflush) → فاتورة صحيحة + خصم مخزون بلا ازدواج + الثوابت خضراء |
| **RC-3 — الأدوار + الطلب المشترك + KDS + real-time** | صلاحيات `pos-waiter/kitchen/cashier` + شاشة الجرسون (فتح/إضافة/إرسال) + شاشة KDS (Preparing/Ready) + `PosHub` (SignalR) لحظيًا + توجيه المحطات | الجرسون يرسل → المطبخ يرى فورًا → «جاهز» يظهر للجرسون؛ الدفع محصور بالكاشير؛ بلا أثر محاسبي قبل الدفع |
| **RC-4 — Modifiers** | `ModifierGroup`/`ModifierOption`/`ItemModifierGroup` + ربطها + خصمها الصحيح عند الدفع | خيار (بديل/إضافة) يُضاف للسطر، يُسعّر ويُخصم صنفه المرتبط |
| **RC-5 — تقسيم الحساب + تيك-أواي/دليفري + شاشة الحالة** | تقسيم/نقل/دمج + أنواع الطلب + شاشة حالة الطلب العامة | فاتورة/فواتير صحيحة بعد التقسيم؛ شاشة الحالة تُحدَّث لحظيًا |
| **RC-6 — الوردية وتقرير Z** | فتح/إقفال وردية + درج نقدية + تقرير Z | نقدية الدرج == المقبوضات |

**أصغر مرحلة أولى تُثبت المسار:** **RC-2** (طلب → دفع الكاشير → فاتورة + خصم مخزون صحيح + GL + Brand، والثوابت خضراء) — تُبنى **RC-1** كتمهيد سريع قبلها. ثم **RC-3** تُدخل الأدوار والطلب المشترك و**KDS اللحظي** (جزء من الأساس، ليس متأخرًا).

> ترتيب البناء: **RC-1 (تمهيد) → RC-2 (المسار الحرج) → RC-3 (أدوار + KDS + real-time) → RC-4 (Modifiers) → RC-5 → RC-6.**

## RC-2 (المسار الحرج) — ⏸️ مؤجَّل/خامل (تصحيح ترتيب)

> **تصحيح ترتيب (باعتماد المستخدم):** ما زلنا في **مرحلة إعداد شكل الكاشير (أدمن)** فقط — **تشغيل الكاشير (بيع/دفع/فاتورة/خصم مخزون) مرحلة لاحقة**. لذلك أُزيلت المسارات التشغيلية (إجراءات الطلب/الدفع في المتحكم + اختبار التطوير + شاشة الكاشير التشغيلية)، وصارت القائمة تشير إلى **`Pos/Preview`** = «معاينة شاشة الكاشير» للقراءة فقط (تبويبات + أزرار + لوحة طلب صورية + شارة «معاينة فقط» + زر دفع معطّل؛ لا بيع). **ما تبقى خاملًا موثّقًا للمرحلة التشغيلية لاحقًا:** الكيانات `PosOrder`/`PosOrderLine`/`PosPayment` + DbSets + `deploy/sql/pos_order.sql` + `PosOrderService` (بما فيه `PayAsync`) + تسجيل DI. التفاصيل أدناه تصف تلك النسخة الخاملة (تُستأنف لاحقًا).

الحالة: **مبني وتم التحقّق منه ثم أُوقف (خامل).** طلب → دفع نقدي → فاتورة + خصم مخزون + قيد، دون أي كاتب GL/مخزون جديد.

**قرارات مُعتمَدة ومُطبَّقة:**
- **التسوية:** فاتورة + تحصيل فوري على **عميل نقدي افتراضي** واحد لكل شركة (`NameEn="POS Walk-in"`). يُعاد استخدام `ReceivableService.CreateSalesInvoiceAsync` (ذمم/إيراد/ض.ق.م + صرف المخزون + COGS عبر `StockService`) ثم `CreateReceiptAsync` (تسوية الذمم → نقدية 110101). الذمم تُفتح وتُقفل فورًا فتبقى `ar_sub` متوازنة.
- **الدفع مرن (`PosPayment`):** كيان عام (OrderId + PaymentMethod + Amount + TargetAccountId + Reference) يقبل عدّة دفعات لكل طلب (يدعم التقسيم مستقبلًا بلا إعادة بناء). **RC-2 نفّذ Cash فقط**؛ البطاقة/كي-نت/مدى/ميزة/آجل/اشتراك تُضاف لاحقًا كأنواع + حساب وجهة فوق نفس البنية.
- **الضريبة:** تُقرأ من النظام القائم — `Item.DefaultTaxCodeId → TaxCode.Rate`، وإلا كود VAT الافتراضي للشركة (`IsDefault`)، وإلا 0. يدعم 0% (الكويت) والإعفاء (VATEX) دون نسبة صلبة. تُرحَّل للمخرجات 210201 عبر الفاتورة.
- **نوع الطلب:** `PosOrder.OrderType` (Dine-in/Takeaway/Delivery) + `TableId` (nullable) موجودان من البداية. RC-2 يشغّل **Takeaway** فقط؛ اختيار الطاولة من المخطط = ملء `TableId` + شاشة في RC-3 (لا تغيير في الأساس).
- **رسوم الخدمة:** `BranchPosSetting.ServiceChargePct` تُضاف كسطر فاتورة (خاضع لض.ق.م الافتراضية).
- **بلا معاملة خارجية في الدفع:** `StockService` يفتح معاملته الخاصة للقفل التشاؤمي؛ التغليف بمعاملة خارجية يرمي استثناء — لذا التركيب تسلسلي مثل باقي النظام (`SellingService.ConvertToInvoiceAsync`).

**الكيانات:** `PosOrder` / `PosOrderLine` / `PosPayment` (`Models/Context/Pos/OperationsPlatform.cs`). المخطط `deploy/sql/pos_order.sql`. الخدمة `IPosOrderService`/`PosOrderService` (Create/AddLine/SetQty/Remove/GetOrder/GetOpenOrder/**PayAsync**). المتحكم `PosController`: `Cashier` (GET) + `PosCreateOrder`/`PosAddLine`/`PosSetQty`/`PosRemoveLine`/`PosPay` (JSON). الشاشة `Views/Pos/Cashier.cshtml` (أزرار لمس بالتبويبات يسارًا + الطلب الجاري يمينًا + Swal تأكيد + toastr). القائمة «الكاشير (نقطة البيع)».

**التحقّق:** `pos-order-test?key=seed123` → 17/17 PASS (طلب مفتوح = صفر قيود/مخزون؛ الدفع: فاتورة+خصم 2/3+COGS+ذمم صفر+نقدية بالإجمالي+ض.ق.م مخرجات+ميزان متوازن). `inv-test-integrity` failedCount=2 بلا زيادة. مثال: فرعي 210 + خدمة 21 + ض.ق.م 32.34 = **263.34**.

**التالي: RC-3** — الأدوار (جرسون/مطبخ/كاشير) + الطلب المشترك + KDS + التحديث اللحظي (SignalR) + اختيار الطاولة من المخطط.
