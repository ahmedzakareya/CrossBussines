# CrossBuy — تحليل معماري: منصة العمليات متعددة الأنشطة + طبقة العلامة التجارية (Brand)

**النوع:** وثيقة تخطيط معماري مسبق — **مرجع تصميم فقط، لا كود ولا تعديل قاعدة بيانات.**
**الحالة:** مسودة تحليل جاهزة للاعتماد عند الوصول لبناء المنصة (المستوى 2 من الرؤية).
**التاريخ:** 2026-07-01 · **يُقرأ مع:** `CrossBuy_Operations_Manual.html`, `CrossBuy_MultiCurrency_Compliance.md`, وذاكرة المشروع (unified-navigation, multicurrency-module).

> ⚠️ **قرار محوري مؤجّل التنفيذ:** يجب حسم أسئلة القسم (3) **قبل** كتابة أي كود للمنصة، لأنها تحدّد شكل الجداول والثوابت. هذه الوثيقة تطرح الخيارات وتوصية أولية لكل منها — القرار النهائي للمالك.

---

## 0) الوضع القائم (نقطة الانطلاق)

| العنصر | الحالة الفعلية |
|---|---|
| الهيكل | `Companies` (CompanyID) → `Branch` (ID, **CompanyID**) — علاقة مباشرة شركة→فرع |
| شجرة تنظيمية | `Hierarchicals` (H_Type: 1 شركة، 2 فرع، 3 إدارة، 4 وظيفة، 5 موظف) — أساس الفروع/مراكز التكلفة والموافقات |
| العملة | لكل فرع عملة وظيفية (`Branch.FunctionalCurrencyId` + `CurrencyLockedAt`) |
| صورة الفرع | `Branch.ImageUrl` · صورة الشركة `Companies.CompanyImage` |
| لا يوجد | **أي كيان Brand أو Group** — نبدأ من الصفر |

**المبدأ الحاكم:** أي إدراج لطبقة جديدة يجب أن يكون **إضافيًا (additive) ومتوافقًا رجعيًا** — النظام الحالي أحادي العلامة ضمنيًا، ويجب أن يظل يعمل بلا علامات حتى تُفعَّل.

## 1) طبقة Brand بين الشركة والفرع

### الهيكل المستهدف
```
Group (مجموعة) ──< Brand (علامة) ──< Location (موقع/فرع)
   │                  │                    │
Companies         Brand (جديد)          Branch (قائم + BrandId?)
```
ملاحظة: «المجموعة» يمكن أن تُمثَّل بـ **`Companies` نفسها** (الكيان القانوني/المجموعة الأم) بدل إدخال كيان Group ثالث الآن — فيصبح عمليًّا: **Company (=Group) → Brand → Branch (=Location)**. هذا يقلّل التعقيد ويكفي معظم الحالات.

### القرار المقترح (بنية الإدراج)
- **كيان جديد `Brand`** يحمل `CompanyId` (ينتمي لمجموعة/شركة).
- **`Branch` يكتسب عمودًا `BrandId int? NULL`** (nullable عمدًا للتوافق الرجعي).
- **الفروع القائمة تبقى `BrandId = NULL`** = «بلا علامة / العلامة الافتراضية» — تعمل تمامًا كما الآن.
- عند التفعيل: تُنشأ علامة افتراضية لكل شركة، ويُمكن (اختياريًا) ترحيل الفروع القائمة إليها بعملية واحدة صريحة — **دون إجبار**.

### التوافق الرجعي (كيف لا ينكسر شيء)
1. `BrandId` **nullable** → لا ترحيل إجباري، ولا كسر لصفوف قائمة.
2. كل استعلام حالي يعمل بمنطق الشركة/الفرع كما هو؛ **مرشّح العلامة يُضاف كطبقة اختيارية** (`brandId == null || x.BrandId == brandId`).
3. شجرة `Hierarchicals`: تُضاف قيمة نوع جديدة **`H_Type = 6 (Brand)`** تُدرَج بين الشركة (1) والفرع (2) — دون تغيير الأنواع القائمة. الفروع بلا علامة تبقى معلّقة مباشرة تحت الشركة كما الآن.
4. القائمة الموحّدة (unified-navigation) والصلاحيات تُصفّى بالعلامة عند وجودها فقط.

**التوصية الأولية:** `Brand{ CompanyId }` + `Branch.BrandId (nullable)` + علامة افتراضية عند التفعيل + `H_Type=6` في الشجرة. **بدون Group منفصل الآن** (الشركة = المجموعة).

## 2) هوية العلامة (Brand Identity)

`Brand` ليس اسمًا فقط، بل هوية بصرية وقانونية كاملة تظهر على كل مخرجات العلامة.

### حقول الكيان `Brand` (مقترحة — للتوثيق فقط)
| المجموعة | الحقول |
|---|---|
| تعريف | `CompanyId`, `Code`, `NameAr`, `NameEn`, `IsActive` |
| هوية بصرية | `LogoPath` (مسار ملف)، `ColorPrimary`, `ColorSecondary`, `ColorAccent` (hex) |
| بيانات المستندات | `LegalName` (الاسم التجاري/القانوني)، `TaxRegNo` (الرقم الضريبي — إن كانت كيانًا قانونيًا)، `Address`, `Phone`, `Email`, `Website`, `CommercialRegNo` |
| مالية | `DefaultCurrencyId` (اختياري — وإلا يرث من الفرع)، `ReceiptFooterAr/En` (نص تذييل الإيصال) |

### تخزين اللوجو والألوان
- **اللوجو:** ملف يُرفع إلى `/uploads/brands/` (نفس نمط `EmployeeService`/`HrDocumentService`: `IWebHostEnvironment.WebRootPath` + مسار نسبي محفوظ في `LogoPath`). لا تُخزَّن الصورة في القاعدة.
- **الألوان:** قيم hex نصية؛ تُحقَن في واجهة العلامة عبر CSS variables (`--brand-primary` …) دون إنشاء CSS مخصّص (اتساقًا مع تفضيل Metronic الصافي).

### أين تظهر الهوية
| السطح | ما يظهر |
|---|---|
| **إيصال/فاتورة الكاشير (POS receipt)** | اللوجو + `LegalName` + `TaxRegNo` + العنوان/التواصل + تذييل العلامة |
| **واجهة المتجر الأونلاين** | اللوجو + ألوان الهوية (ثيم) + بيانات التواصل |
| **شاشة الكاشير (POS terminal)** | اللوجو + الألوان (ترويسة الشاشة) |
| **شاشة المطبخ (KDS)** | اللوجو مصغّر + لون العلامة لتمييز الطلبات عند تعدّد العلامات في مطبخ مشترك |
| **الفاتورة الضريبية الرسمية / ETA** | إن كانت العلامة كيانًا قانونيًا: `TaxRegNo` الخاص بها؛ وإلا `TaxRegNo` الشركة (انظر القسم 3-هـ) |

**التوصية الأولية:** هوية كاملة على مستوى `Brand` مع **وراثة من الشركة عند غياب أي حقل** (fallback)، فتعمل العلامات البسيطة بلا إدخال مكرّر.

## 3) الأسئلة المعمارية الواجب حسمها (خيارات + توصية أولية)

> كل بند: الخيارات، الأثر، والتوصية الأولية. **لا قرار نهائيًا الآن.**

### (أ) المخزون — منفصل لكل علامة أم مشترك؟
- **خيار 1 — مخزون مشترك (على مستوى الشركة):** المخازن كما هي، والعلامات تسحب من نفس الرصيد. أبسط، يناسب مجموعة بمستودع مركزي.
- **خيار 2 — مخزون منفصل لكل علامة:** كل علامة لها مخازنها؛ `Warehouse.BrandId`. يناسب علامات مستقلة تجاريًا/قانونيًا.
- **خيار 3 — هجين (موصى به):** المخزون يُمسك على مستوى **المخزن**، والمخزن يُنسب لعلامة اختياريًا (`Warehouse.BrandId nullable`). فالمشترك = مخزن بلا علامة، والمنفصل = مخزن بعلامة. يحافظ على ثابت المخزون==GL دون فرض نموذج واحد.
- **التوصية:** **خيار 3** — يغطّي الحالتين بمرونة، ولا يكسر `stock_gl`/`fifo_layers` (الرصيد يبقى لكل مخزن).

### (ب) المحاسبة/التقارير — ربحية بالعلامة أم بالشركة فقط؟
- **خيار 1 — بالشركة فقط:** كما الآن. لا ربحية علامة.
- **خيار 2 — العلامة = بُعد تحليلي (موصى به):** تُعامَل العلامة كـ **مركز تكلفة/بُعد** فوق الآلية القائمة (`CostCenter`/`Hierarchicals`)، فتظهر قوائم دخل وربحية لكل علامة **دون دفاتر منفصلة**. القيود تبقى في نفس دفتر الشركة مع وسم `BrandId`/CostCenter.
- **خيار 3 — دفاتر منفصلة لكل علامة:** فقط إن كانت كيانًا قانونيًا مستقلًا (انظر 3-هـ) — أثقل بكثير.
- **التوصية:** **خيار 2** — يعيد استخدام مراكز التكلفة القائمة، يعطي ربحية العلامة، ويحافظ على `tb_balanced` وثابت الدفتر الواحد.

### (ج) العملاء — موحّد أم منفصل لكل علامة؟
- **خيار 1 — عميل موحّد عبر كل العلامات (موصى به):** `Customer` على مستوى الشركة؛ العلامة تُوسَم على المستند (الفاتورة/الطلب) لا على العميل. يعطي رؤية 360° للعميل عبر العلامات (مهم لـ CRM والولاء).
- **خيار 2 — عملاء منفصلون لكل علامة:** `Customer.BrandId`. عزل تام، لكن يفقد الرؤية الموحّدة ويكرّر البيانات.
- **التوصية:** **خيار 1** — عميل موحّد + وسم العلامة على المعاملة. (يمكن لاحقًا تقييد رؤية مندوب علامة عبر نفس نمط `CrmAccessService`.)

### (د) التسعير — قائمة لكل علامة أم مشتركة؟
- محرّك التسعير الحالي يدعم بالفعل استهدافًا متعدّد المستويات (عميل/شريحة/عملة/أولوية) + عروض (2B) + تكلفة‑زائد (2C).
- **خيار 1 — قوائم مشتركة مع استهداف علامة:** إضافة `PriceList.BrandId nullable`؛ القائمة بلا علامة = عامة، وبعلامة = خاصة بها. يعيد استخدام كل المحرّك.
- **خيار 2 — قوائم منفصلة تمامًا لكل علامة:** عزل كامل، لكن تكرار.
- **التوصية:** **خيار 1** — `BrandId` كبُعد استهداف إضافي في `PriceList` (والعروض)، ضمن ترتيب الأولوية القائم (علامة > عميل > شريحة > عام). طبيعي جدًّا لأن كل علامة «مرتبطة بقائمة أسعارها».

### (هـ) الكيان القانوني — علامة مستقلة قانونيًا أم اسم تجاري؟
- **خيار 1 — اسم تجاري تحت نفس الكيان القانوني (موصى به كافتراضي):** كل العلامات تشترك في `TaxRegNo`/الدفاتر الخاصة بالشركة؛ العلامة تغيّر فقط الهوية الظاهرة (لوجو/اسم تجاري/تذييل) على الإيصال. أبسط، دفتر واحد، `tb_balanced` محفوظ.
- **خيار 2 — كيان قانوني منفصل:** لكل علامة `TaxRegNo` وربما دفاتر/تسلسل فواتير مستقل وملف ETA خاص. يلزم لو كانت شركات مستقلة فعلًا. الأثر: ترقيم فواتير لكل علامة، تقارير ضريبية لكل علامة، وربما فصل GL (خيار 3-ب).
- **التوصية:** **دعم الوضعين عبر علم `Brand.IsLegalEntity`**: افتراضيًا false (اسم تجاري)؛ عند true تُفعَّل بيانات ضريبية وترقيم مستقلّان. الإيصال يقرأ `TaxRegNo` من العلامة إن كانت كيانًا قانونيًا، وإلا من الشركة.

## 4) الأثر على النواة القائمة (نقاط مراعاة BrandId)

| الموديول | الأثر | كيف بلا كسر الثوابت |
|---|---|---|
| **المخزون/المخازن** | `Warehouse.BrandId?` (هجين) | الرصيد يبقى لكل مخزن → `stock_gl`/`fifo_layers`/`transit_zero` بلا مساس؛ العلامة مرشّح عرض/تخصيص |
| **المبيعات/الفواتير/الطلبات** | وسم `BrandId?` على رأس المستند | القيد يبقى في دفتر الشركة؛ العلامة = بُعد (CostCenter) → `ar_sub`/`tb_balanced` محفوظة |
| **التسعير + العروض** | `PriceList.BrandId?` / `Promotion` استهداف علامة | يعيد استخدام محرّك `PricingService`؛ الأولوية تضيف طبقة العلامة أعلى العميل |
| **التقارير/القوائم** | تجميع اختياري بالعلامة | عبر مراكز التكلفة القائمة؛ لا دفاتر جديدة |
| **CRM** | العميل موحّد؛ رؤية بالعلامة اختيارية | نفس نمط `CrmAccessService.VisibleOwnerIdsAsync` |
| **المحاسبة/ETA** | ترقيم/ضريبة لكل علامة **فقط** عند `IsLegalEntity` | الافتراضي دفتر/رقم ضريبي واحد → لا تغيير |
| **الصلاحيات + القائمة** | تصفية بالعلامة عند وجودها | `Access` services تضيف مرشّح `BrandId` اختياري |
| **التصنيع** | أوامر التصنيع تُنسب لعلامة/موقع اختياريًا | WIP/GL (1105/520108) بلا مساس؛ العلامة بُعد |

**القاعدة الذهبية للثوابت:** BrandId يُضاف **دائمًا كعمود nullable + بُعد تحليلي**، ولا يغيّر أبدًا **من يكتب في GL** (`JournalEntryService`) أو **من يكتب المخزون** (`StockService`). كل التجميع بالعلامة يتم عبر مراكز التكلفة/الوسوم، فتظل فحوص السلامة الثمانية خضراء.

## 5) بقية عناصر المنصة (خطوط عريضة للربط)

كلها تتعلّق بطبقة **Brand → Location**، وتطبّق **هوية العلامة (لوجو/ألوان/بيانات)** تلقائيًا:

- **رسم المكان (Floor Plan):** مخطّط طاولات/مناطق **لكل Location**؛ يرث علامة الموقع. يُستخدم لإسناد الطلبات للطاولات وحالة الإشغال. (كيان `FloorTable{ LocationId, Zone, Seats, X, Y }` لاحقًا.)
- **الكاشير متعدد الأنشطة (POS):** واجهة الكاشير تُحمِّل **علامة الموقع** (لوجو/ألوان/تذييل الإيصال) وقائمة أسعارها. نوع النشاط (مطاعم/تجزئة/…) يبدّل تخطيط الشاشة وسير العمل — **لكن كل نوع نشاط له تصميمه** (يُدرَس منفصلًا؛ لا تصميم موحّد مفترض).
- **شاشة المطبخ (KDS):** تستقبل بنود الطلبات المطبخية للموقع؛ تلوّن/توسم بالعلامة عند مطبخ مشترك بين علامات. مرتبطة بـ Location (والعلامة عبره).
- **إدارة طلبات الطاولات:** تربط Floor Plan × POS × KDS؛ الطلب يحمل `LocationId` (ومنه `BrandId`)، ويظهر بهوية العلامة على الإيصال.
- **الربط بالتصنيع:** أصناف مُصنّعة/مجمّعة (وصفات المطبخ = BOM) تُستهلك عند البيع (backflush) عبر آلية التصنيع القائمة؛ الموقع/العلامة بُعد على أمر الإنتاج، وتكلفة الوصفة تغذّي تكلفة‑زائد (2C) لو رُغب.

**نمط تطبيق الهوية:** أي سطح عرض (إيصال/كاشير/KDS/أونلاين) يستقبل `LocationId` → يحلّ `BrandId` → يحمّل `Brand` (لوجو/ألوان/بيانات، مع fallback للشركة) → يحقنها في القالب. مصدر واحد للهوية، لا تكرار.

---

## 6) الخلاصة والقرارات المطلوبة قبل البناء

**البنية المقترحة (للاعتماد):** `Brand{ CompanyId + هوية كاملة + IsLegalEntity }` · `Branch.BrandId nullable` · `H_Type=6` · العلامة **بُعد تحليلي** (لا دفاتر منفصلة إلا عند كيان قانوني) · العميل موحّد · التسعير/المخزون بمرشّح علامة اختياري (هجين) · الثوابت تُحمى بإبقاء BrandId عمودًا nullable + وسمًا لا كاتبًا في GL/المخزون.

**يجب حسمه صراحةً قبل الكود:** (أ) نموذج المخزون، (ب) ربحية العلامة، (ج) نموذج العميل، (د) نموذج التسعير، (هـ) الكيان القانوني — القسم (3). وأيضًا: هل نحتاج كيان **Group** ثالثًا فعلًا أم تكفي الشركة كمجموعة؟

**قرار POS الحرج (قائم):** POS ليس موديولًا واحدًا — **دراسة معمارية منفصلة لأنواع الأنشطة (مشترك/مختلف) قبل أي بناء.** هذه الوثيقة تمهّد لطبقة Brand فقط.
