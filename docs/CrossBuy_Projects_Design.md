# CrossBuy — موديول المشاريع والمقاولات (Projects & Contracting)
## وثيقة تصميم الأساس (المشروع + مركز التكلفة)

> **الحالة:** مسودّة للمراجعة — **لا كود بعد**. نطرح نقاط الحسم بخيارات + توصية. بعد موافقة المستخدم نبدأ التنفيذ مرحلة بمرحلة.
> **المبدأ الحاكم:** النظام مرن — المستخدم يختار نوع نشاطه (لا نفترض نوع مقاولات واحد).

---

## 0) خلاصة التحقّق (ما هو موجود بالفعل)

| العنصر | الحالة | التفاصيل |
|---|---|---|
| **مراكز التكلفة `CostCenter`** | ✅ موجود | كيان في `Dimensions.cs` (Code/Name/Parent/`SourceHierarchicalId`/IsActive) + `CostCenterService` (شجرة + `SeedFromHierarchyAsync` من الهيكل التنظيمي). **مرتبطة بشجرة المنشأة (فروع/إدارات) لا بالمشاريع.** |
| **الربط بالقيود** | ✅ موجود | `JournalEntryLine.CostCenterId` + `ProjectId` + `EmployeeId` (كلها nullable). `JournalEntryService` يكتبها من `JournalLineInput`. الحساب يمكن أن يفرض `RequireCostCenter`/`RequireProject`. |
| **بُعد المشروع `Project`** | ✅ موجود ومُفعّل | كيان `Project` (Code/Name/IsActive/StartDate/EndDate/Budget) + `ProjectService` (CRUD + `ProfitabilityAsync`). |
| **تدفّق ProjectId للـ GL** | ✅ شغّال end-to-end | فواتير البيع/الشراء + SO/PO (headers) + **COGS** (عبر `MovementRequest.ProjectId` في `StockService.PostGlAsync`) + القيد اليدوي. الإيراد وتكلفته يحملان نفس ProjectId. |
| **تقرير ربحية المشروع** | ✅ موجود | `ProfitabilityAsync`: إيراد 4xxx − تكلفة 5xxx لكل مشروع مقابل الموازنة + شاشة `Views/Project/Profitability.cshtml`. |
| فواتير تحمل `CostCenterId` header | ✅ | مرآة لبُعد المشروع. |

**النتيجة الحاسمة:** آلية **نسب التكلفة/الإيراد للمشروع موجودة وشغّالة**. الموديول الجديد **يبني فوق `Project` القائم** — لا يخترع بُعدًا جديدًا ولا كاتب محاسبة جديد.

## 1) كيان المشروع Project — التصميم

الكيان `Project` موجود لكنه «خفيف» (بُعد تحليلي). للمقاولات نحتاج حقول إضافية. **التوصية: نمدّد نفس الكيان بأعمدة nullable إضافية** (لا كيان جديد) حتى تبقى كل سباكة ProjectId + تقرير الربحية شغّالة بدون تغيير.

الحقول المطلوب إضافتها (كلها إضافية/nullable — لا تكسر شيئًا):

| الحقل | النوع | ملاحظة |
|---|---|---|
| `CustomerId` | `int?` | العميل = عميل AR قائم (إعادة استخدام `Customer`)، لا كيان عميل جديد. |
| `Location` | `string?` | موقع المشروع (نص حر). |
| `ContractValue` | `decimal?` | قيمة العقد الإجمالية. |
| `Status` | `string` | حالة المشروع (lookup/قائمة ثابتة صغيرة: Draft/Active/OnHold/Completed/Cancelled). |
| `ActivityTypeId` | `int?` | **نوع النشاط — يختاره المستخدم (مرن)** — انظر بند 3. |
| `CostCenterId` | `int?` | ربط اختياري بمركز تكلفة (rollup تنظيمي) — انظر بند 2. |
| `ManagerEmployeeId` | `int?` | مدير المشروع (اختياري، إعادة استخدام `Employee`). |
| (`StartDate`/`EndDate`/`Budget`/`Code`/`Name` موجودة بالفعل) | | تُعاد استخدامها كما هي. |

> Schema: ملف SQL إضافي `deploy/sql/projects_contracting.sql` (ALTER … ADD إن لم يوجد) — على نمط `project_dimension.sql`.

## 2) ربط المشروع بمركز التكلفة — نقطة حسم (1)

**السياق:** مراكز التكلفة موجودة لكنها مربوطة بالهيكل التنظيمي (فرع/إدارة)، بينما **بُعد ProjectId موجود ومربوط بالكامل بالـ GL + تقرير ربحية جاهز**.

| الخيار | الوصف | إيجابيات | سلبيات |
|---|---|---|---|
| **أ — (موصى به) نعتمد ProjectId القائم للنسب** | التكلفة/الإيراد تُنسب للمشروع عبر `ProjectId` (المسار الموجود شغّال end-to-end). ربط المشروع بمركز تكلفة يبقى **اختياريًا فقط** (`Project.CostCenterId` nullable) لتجميع تنظيمي عند الحاجة. | يعيد استخدام سباكة جاهزة ومختبرة + تقرير ربحية جاهز؛ صفر مخاطرة على الثوابت؛ لا كاتب جديد. | مركز التكلفة يظل بُعدًا تنظيميًا منفصلًا (طبيعي). |
| ب — كل مشروع = مركز تكلفة مخصّص | إنشاء `CostCenter` تلقائي لكل مشروع والنسب عبر `CostCenterId`. | يوافق حرفية «كل مشروع = مركز تكلفة». | يكرّر ما يفعله ProjectId؛ `CostCenter` مرتبط بـ `SourceHierarchicalId` (شجرة تنظيمية) ولا يناسب مشروعًا؛ يتطلب إعادة توصيل النسب. |

**التوصية: الخيار أ.** النسب عبر `ProjectId` (قائم)، وربط `Project.CostCenterId` اختياري للـ rollup. لا نبني آلية نسب جديدة.

---

## 3) مرونة نوع النشاط — نقطة حسم (2)

المطلوب: المستخدم يختار نشاطه (مقاولات إنشائية/طرق/كهروميكانيكا/صيانة/تكنولوجيا/فعاليات…) — **لا نوع مفترض**.

| الخيار | الوصف | التوصية |
|---|---|---|
| **أ — (موصى به) جدول lookup `ProjectActivityType`** | جدول صغير (Code/Name/NameEn/IsActive) **يبدأ فارغًا**، والمستخدم يعرّف أنواعه بنفسه؛ `Project.ActivityTypeId` يشير إليه. | مرن تمامًا، لا شيء مثبّت في الكود، شاشة CRUD بسيطة على نمط الحسابات. |
| ب — نص حر على المشروع | `Project.ActivityType` نص. | أبسط لكن بلا توحيد/تصفية. |

**التوصية: الخيار أ** (lookup فارغ يملؤه المستخدم) — يحقّق «النظام مرن» دون افتراض.

## 4) كيف تُنسب التكاليف/الإيرادات وتُحسب الربحية

**كلها عبر الخدمات القائمة فقط — لا كاتب محاسبة جديد:**

- **الإيراد:** فاتورة بيع/مستخلص تُنشأ بـ `ProjectId` → `ReceivableService`/`JournalEntryService` يضعان ProjectId على سطور الإيراد/AR/VAT (المسار موجود).
- **تكلفة المواد:** صرف مخزون على المشروع عبر `StockService` + `MovementRequest.ProjectId` → سطور المخزون/التكلفة تحمل ProjectId (المسار موجود).
- **العمالة/التايم‑شيت:** إعادة استخدام موديول المهام/التايم‑شيت القائم (تكلفة العمالة موجودة) موسومة بالمشروع.
- **الباطن/مصروفات أخرى:** فاتورة شراء/قيد بـ ProjectId (المسار موجود).
- **الربحية:** `ProjectService.ProfitabilityAsync` (إيراد 4xxx − تكلفة 5xxx مقابل الموازنة) — **جاهز**؛ نبني عليه تقرير المقاولات (موازنة/فعلي/متبقٍ/نسبة إنجاز) لاحقًا.

> **الثابت الذهبي:** `ProjectId` و`CostCenterId` **nullable ولا يغيّران ترحيل الـ GL/المخزون إطلاقًا** → `inv-test-integrity = 0` يظل أخضر.

## 5) التقسيم المرحلي المقترح للموديول (كل مرحلة تُبنى وتُختبر وتُوقف)

| # | المرحلة | المحتوى | الخدمات المُعاد استخدامها |
|---|---|---|---|
| **P0** | **الأساس (هذه الوثيقة)** | تمديد `Project` (عميل/موقع/قيمة عقد/حالة/نوع نشاط) + lookup أنواع النشاط + ربط اختياري بمركز تكلفة + شاشة CRUD (نمط الحسابات) | ProjectService (موسّع) |
| P1 | **BOQ / بنود الأعمال** | جدول بنود (وصف/وحدة/كمية/سعر) لكل مشروع = أساس العقد والمستخلصات | — (بيانات فقط) |
| P2 | **العقد** | ربط البنود بقيمة العقد + الشروط | — |
| P3 | **التنفيذ** | نسب تقدّم/كميات منفّذة لكل بند | — |
| P4 | **صرف المواد** | صرف مخزون على المشروع | `StockService` (+ ProjectId) |
| P5 | **العمالة** | ساعات/تكلفة عمالة على المشروع | موديول المهام/التايم‑شيت القائم |
| P6 | **الباطن (Subcontractors)** | عقود/فواتير باطن على المشروع | `PayableService` |
| P7 | **المستخلصات (Progress Billing)** | فاتورة مرحلية بنسبة الإنجاز على البنود | `ReceivableService` |
| P8 | **الموازنة مقابل الفعلي** | مقارنة الموازنة/العقد بالتكلفة/الإيراد الفعلي | تقارير GL القائمة |
| P9 | **الربحية** | تقرير ربحية المقاولات (يبني على `ProfitabilityAsync`) | ProjectService |
| P10 | **التسليم (Handover)** | إقفال المشروع + مستخلص نهائي | — |

> كل مرحلة: بيانات/منطق فقط، أي قيمة مالية عبر الخدمات القائمة، `inv-test-integrity = 0`، وقفة للمراجعة.

## 6) نقاط الحسم للمراجعة (ملخّص القرارات المطلوبة منك)

1. **آلية النسب:** الخيار **أ** (ProjectId القائم + ربط مركز تكلفة اختياري) — موافق؟
2. **تمديد `Project`** بأعمدة nullable بدل كيان جديد — موافق؟
3. **نوع النشاط:** lookup فارغ يملؤه المستخدم (خيار أ) — موافق؟
4. **العميل** = عميل AR قائم (`CustomerId`) — موافق؟
5. **حالات المشروع:** Draft/Active/OnHold/Completed/Cancelled — تناسبك أم تعدّلها؟
6. **P0 يبدأ بالكيان + الشاشة فقط** (نمط شاشات الحسابات) — والتصميم/الـ UI تعطيه أنت قبل بناء أي شاشة.

---

## 7) القواعد الحاكمة (ثابتة طوال الموديول)

- النظام **مرن**: المستخدم يختار النشاط (لا نوع مقاولات مفترض).
- أي قيمة مالية **عبر الخدمات القائمة فقط**: `StockService` / `JournalEntryService` / `ReceivableService` / `PayableService`. **لا كاتب محاسبة جديد.**
- **إعادة استخدام** الموجود: المهام/التايم‑شيت/المخزون/المحاسبة/العملاء.
- الثوابت سليمة: `ProjectId`/`CostCenterId` دائمًا nullable، لا يغيّران الترحيل، `inv-test-integrity = 0`.
- **التصميم من المستخدم**: لا HTML/CSS مبتكر؛ عند الحاجة لشكل شاشة → **نمط شاشات الحسابات المعتمد**، وأطلب التصميم منك قبل البناء.
