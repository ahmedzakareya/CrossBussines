## 0) ملخّص تنفيذي — تصحيح الصورة

الفحص كشف أن **النواة التشغيلية لدورتي البيع والشراء مكتملة وموصولة بالكامل** بالمخزون والمحاسبة:

- **الطلب‑للتحصيل (O2C):** أمر بيع → إذن صرف (يُرحّل تكلفة المبيعات وإخراج المخزون) → فاتورة بيع (تُرحّل: مدين 1102 ذمم / دائن إيراد + 210201 ض.ق.م مخرجات) → سند قبض. عبر `SellingService` + `ReceivableService`، وجسر `ConvertToInvoiceAsync`.
- **الشراء‑للسداد (P2P):** أمر شراء → إذن استلام (يُرحّل دخول المخزون مقابل 210203 GRNI، **أو** يرسمل أصلًا ثابتًا تلقائيًا إن كان الصنف Asset) → فاتورة شراء (تُصفّي GRNI + ض.ق.م مدخلات 110401) → سند دفع (بدعم ضريبة خصم منبع 210202). عبر `ProcurementService` + `PayableService`.
- **لا ازدواج في البيانات الرئيسية:** كيان `Customer` وكيان `Vendor` **وحيدان** يتشاركهما المخزون والمحاسبة (لا عميل/مورد مكرّر). الازدواج الوحيد منطقي: سطور الأمر مقابل سطور الفاتورة (طبيعي).

**الخلاصة:** ما نبنيه في «المرحلة 3» **ليس** إعادة بناء البيع/الشراء، بل **الطبقات الأمامية والتحكمية الغائبة**: التسعير، عروض الأسعار، المرتجعات وإشعارات الدائن/المدين، فرض حدّ الائتمان، إثراء بيانات العميل/المورد، ومطابقة ثلاثية رسمية — ثم (اختياريًا) وحدة CRM كاملة (عملاء محتملون/فرص/خط أنابيب).

## 1) المبني فعلًا (بالأدلة)

### 1.1 المبيعات ✔
- **مخزون:** `SalesOrder`/`SalesOrderLine`, `DeliveryNote`/`DeliveryNoteLine` (`Models/Context/Inventory/Inventory.cs`). خدمة `SellingService` (BL): إنشاء أمر بيع (حالة Approved)، إذن صرف يُرحّل حركة مخزون Direction=-1 + تكلفة المبيعات، تحديث `DeliveredQty`، جسر `ConvertToInvoiceAsync`. شاشات `InventoryController`: SalesOrders/NewSalesOrder/Deliveries/…
- **محاسبة:** `Customer`, `SalesInvoice`/`SalesInvoiceLine`, `Receipt` (`Models/Context/Accounting/ReceivablesPayables.cs`). خدمة `ReceivableService`: `CreateSalesInvoiceAsync` (ترحيل AR/إيراد/ض.ق.م + إخراج مخزون عند وجود ItemId)، `CreateReceiptAsync`، `AgingAsync` (تقادم FIFO). شاشات `AccountingController`: Customers/SalesInvoices/Receipts/CustomerStatement/ArAging.
- **خصم سطري** متاح عبر `DiscountAmount` في كل المستندات.

### 1.2 المشتريات ✔
- **مخزون:** `PurchaseOrder`/Line, `GoodsReceipt`/Line. خدمة `ProcurementService`: أمر شراء، إذن استلام (Direction=+1 مقابل GRNI 210203)، **ترسيم أصل تلقائي** إن `Item.ItemType=Asset`، جسر `ConvertToInvoiceAsync`.
- **محاسبة:** `Vendor`, `PurchaseInvoice`/Line, `Payment`. خدمة `PayableService`: `CreatePurchaseInvoiceAsync` (تصفية GRNI/مصروف/مخزون + ض.ق.م مدخلات)، `CreatePaymentAsync` (بدعم WHT 210202)، `AgingAsync`.

### 1.3 المخزون والأصول والضرائب ✔
تكلفة (متوسط متحرك/FIFO)، تتبّع تشغيلة/سيريال/صلاحية، جرد ومعالجة فروقات، إهلاك ومصاريف نقل (Landed)، أرصدة افتتاحية، موافقات وصلاحيات RBAC، ض.ق.م وإقرارات، ETA (stub). كلها مبنية (راجع وثيقة المخزون).

## 2) الناقص الحقيقي (بالأولوية والتكامل)

### 2.1 إثراء بيانات العميل/المورد — ◐ 🟠
`Customer`/`Vendor` يحملان: الاسم، الرقم الضريبي، العنوان، حساب التحكم، العملة، مهلة السداد، (وحدّ ائتمان للعميل). **ناقص:** هاتف/بريد/شخص اتصال، تصنيف/شريحة، فصل عنوان الفوترة عن الشحن. **رخيص ومنفصل** ويفتح الباب للتقارير والـ CRM.

### 2.2 عروض الأسعار (Quotations) — ✘ 🟠
لا كيان `Quotation`. دورة البيع تبدأ من «أمر البيع» مباشرة. المطلوب: عرض سعر (مسودة/مُرسَل/مقبول/منتهٍ) قابل للتحويل إلى أمر بيع — **يعيد استخدام آلية أمر البيع** بالكامل.

### 2.3 المرتجعات وإشعارات الدائن/المدين — ✘ 🟠
لا `SalesReturn`/`CreditNote` ولا `PurchaseReturn`/`DebitNote`. لا يمكن حاليًا عكس فاتورة أو رد بضاعة محاسبيًا/مخزنيًا. المطلوب: مرتجع بيع (إدخال مخزون + إشعار دائن يعكس AR/الإيراد/الضريبة) ومرتجع شراء (إخراج مخزون + إشعار مدين يعكس AP). **يعيد استخدام `JournalEntryService` + `StockService` (عكس الإشارة).**

### 2.4 محرّك التسعير — ✘ 🟡
يوجد `Item.SalesPrice` (سعر ثابت واحد) وخصم سطري يدوي فقط. **ناقص:** قوائم أسعار، تسعير حسب العميل، قواعد خصم (كمية/شريحة/مدة). تكامل: يغذّي أمر البيع/الفاتورة بالسعر.

### 2.5 فرض حدّ الائتمان — ✘ 🟠
حقل `Customer.CreditLimit` موجود **بلا أي فرض**. المطلوب: عند إنشاء أمر بيع/فاتورة، تحذير/منع إذا (رصيد الذمم الحالي + قيمة المستند) > الحد. **رخيص** ويعيد استخدام منطق التقادم/الأرصدة. نمط حوكمي مثل حد اعتماد القيود.

### 2.6 المطابقة الثلاثية الرسمية (3-Way Match) — ◐ 🟡
الربط موجود بمفاتيح (PO↔GR↔PI) لكن **بلا تحقق آلي** من تطابق الكميات/الأسعار ضمن سماحية قبل ترحيل فاتورة الشراء. المطلوب: فحص تفاوت (Qty/Price tolerance) وتنبيه/منع.

### 2.7 وحدة CRM كاملة — ✘ 🟡 (الأكبر، اختياري)
لا عملاء محتملون/فرص/خط أنابيب/أنشطة/حملات. هذه وحدة قائمة بذاتها (Lead → Opportunity → Quote → Order). **الأثقل والأقل ارتباطًا بنواة الـ ERP** — يُبنى فقط إن طُلب صراحةً (مثل قاعدة التصنيع: نسأل أولًا).

### 2.8 تحليلات العميل — ✘ 🟡
كشف حساب وتقادم موجودان؛ ناقص: ربحية العميل، قيمة العمر، تحليل الشرائح. يعتمد على 2.1.

## 3) سلسلة الاعتماد (ليه الترتيب ده)

```
إثراء العميل/المورد (2.1) ──┬─► عروض الأسعار (2.2) ──► أمر البيع (مبني)
                            │
حدّ الائتمان (2.5) ─────────┘   (يحرس أمر البيع/الفاتورة)

المرتجعات + دائن/مدين (2.3) ──► تعكس الفاتورة + المخزون (مبنيان)
محرّك التسعير (2.4) ──────────► يغذّي الأسعار (تحسين، غير حابس)
المطابقة الثلاثية (2.6) ──────► تحرس فاتورة الشراء
CRM كامل (2.7) ──────────────► طبقة أمامية مستقلة (اختياري)
```

## 4) خطة المراحل المقترحة

| مرحلة | المحتوى | الأولوية | يتكامل مع |
|---|---|---|---|
| **P3-1** | إثراء `Customer`/`Vendor` (هاتف/بريد/جهة اتصال/شريحة/عنوان شحن) + إظهارها في الشاشات | 🟠 رخيص | الفواتير، الكشوف، CRM |
| **P3-2** | عروض الأسعار (Quotation→SalesOrder) معيدًا استخدام آلية أمر البيع | 🟠 | المبيعات (مبني) |
| **P3-3** | المرتجعات: مرتجع بيع + إشعار دائن، مرتجع شراء + إشعار مدين (عكس GL + مخزون) | 🟠 | المحاسبة + المخزون |
| **P3-4** | فرض حدّ الائتمان عند أمر البيع/الفاتورة (تحذير/منع) | 🟠 رخيص | الذمم |
| **P3-5** | محرّك التسعير: قوائم أسعار + تسعير حسب العميل + قواعد خصم | 🟡 | المبيعات |
| **P3-6** | المطابقة الثلاثية الرسمية (سماحية Qty/Price قبل ترحيل فاتورة الشراء) | 🟡 | المشتريات |
| **P3-7** | وحدة CRM (Lead→Opportunity→Pipeline→أنشطة) — **يُسأل قبلها** | 🟡 اختياري | المبيعات، العميل |

**التوصية للبدء:** P3-1 (إثراء العميل/المورد) — رخيص ومنفصل ويفتح الباقي — ثم P3-2 (عروض الأسعار) و P3-3 (المرتجعات) كأكثر بنود ERP اكتمالًا للدورة، ثم P3-4 (حد الائتمان). P3-5/P3-6 تحسينات، و P3-7 (CRM) يُبنى عند الطلب فقط.

## 5) نقاط تكامل يجب احترامها (مع المبني)

- **أي قيد محاسبي عبر `JournalEntryService` فقط**؛ أي حركة مخزون عبر `StockService` فقط (المرتجعات = عكس الإشارة، لا منطق GL/مخزون جديد).
- **العميل/المورد كيان وحيد مشترك** — لا تُنشئ كيان عميل/مورد جديد للـ CRM؛ أضِف حقولًا أو كيان `Contact` مرتبطًا.
- **عروض الأسعار تعيد استخدام `SellingService`/أمر البيع** — لا دورة بيع موازية.
- **الثوابت:** المرتجعات وإشعارات الدائن/المدين تتسق مع حسابات التحكّم (1102/2101) والمخزون (1103) — يُراقَب بحارس السلامة (inv-test-integrity).
- **الحوكمة:** فرض حد الائتمان والمطابقة الثلاثية على نمط حدود الاعتماد القائمة (تحذير/منع برسالة واضحة، RBAC حيث يلزم).
- **AR/EN + Metronic صافي + بحث حقيقي + لا بيانات ثابتة** في كل شاشة جديدة.
- **DECIMAL(19,4)**، سكيمة يدوية sqlcmd ([LineNo] بأقواس، NCHAR)، اسم جدول EF = اسم الـ DbSet (جمع).
- **مؤجَّل بقرار النطاق:** EGP بأعمدة عملة محفوظة؛ شركة واحدة (CompanyID=1) بسكيمة تدعم أكثر؛ عزل ETA.
