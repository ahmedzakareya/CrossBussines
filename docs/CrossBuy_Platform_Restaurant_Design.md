# CrossBuy — وثيقة تصميم تنفيذي: منصة العمليات (POS) — نموذج المطعم

**النوع:** تصميم تنفيذي (Executive Design) — أعمق من الوثيقة المعمارية المبدئية؛ **يحسم القرارات قبل أي كود.**
**الحالة:** مسودة للمراجعة. **لا يوجد كود ولا تعديل قاعدة.** المستوى 2 من الرؤية، نموذج المطعم أولًا ثم التعميم.
**التاريخ:** 2026-07-01 · **يُقرأ مع:** `CrossBuy_MultiActivity_Platform_Architecture.md` (طبقة Brand)، ذاكرة project-dimension / manufacturing / pricing / multicurrency.

> **مبدأ حاكم:** POS **واجهة تشغيلية فوق النواة**، لا نظام محاسبي موازٍ. كل حدث مالي يمرّ عبر الخدمات القائمة (ReceivableService/StockService/JournalEntryService/PricingService) → **الثوابت الثمانية تبقى خضراء**. الطلب عملية تشغيلية؛ الأثر المحاسبي يقع عند التسوية.

---

## 0) ما نبني عليه (موجود فعلًا)
- **الوصفة = BOM:** الطبق صنف مركّب (`Item.IsComposite`, `ItemComponent`)؛ بيعه يخصم مكوّناته (backflush) عبر `StockService` (نمط `AssembleAsync`/التجميع الفوري) → COGS + مخزون.
- **التسعير:** `PricingService.GetPriceAsync` (قوائم أسعار + عروض 2B + تكلفة‑زائد 2C) — قابل للاستهداف بالعلامة عبر `PriceList.BrandId` (مخطّط في وثيقة Brand).
- **العلامة:** `Brand` + `Branch.BrandId` (أساس مبني) → الموقع (Location) = الفرع، يرث العلامة وهويتها (لوجو/ألوان/تذييل إيصال).
- **الأبعاد:** `Project` + `CostCenter` (تتدفّق لسطور القيد). **GL:** `JournalEntryService` الكاتب الوحيد. **المخزون:** `StockService` الكاتب الوحيد.

## 1) معمار الكاشير — القرار الأهم

**المتطلبات:** إضافة صنف < ثانية، شاشة لمس/تابلت، تشغيل متعدد المحطات، مرونة عند انقطاع الشبكة، طباعة إيصال/مطبخ.

| الخيار | الوصف | مزايا | عيوب |
|---|---|---|---|
| **أ) صفحة داخل CrossBuy MVC** | «شاشة كاشير» (Controller + View لمس) تستدعي JSON endpoints داخل نفس التطبيق (نمط `ItemPickData`/`PriceLookup` القائم) | أسرع بناءً، يعيد استخدام الجلسة/الصلاحيات/الخدمات مباشرة، نشر واحد | JS ثقيل داخل MVC، لا offline حقيقي بسهولة |
| **ب) SPA منفصلة (React/Blazor) تستهلك REST API** | واجهة مستقلة + طبقة API رسمية | تجربة أسرع/أنعم، تمهّد للموبايل والأوفلاين | يتطلب بناء طبقة API كاملة + مصادقة رمزية + مشروع/نشر ثانٍ — كلفة عالية الآن |
| **ج) هجين: صفحة POS مخصّصة (SPA خفيفة داخل MVC) + endpoints JSON** | صفحة واحدة touch-first، حالة الطلب على العميل، نداءات JSON دقيقة (add-line/send-kitchen/pay)، تعزل «حالة الطلب» لتتيح offline لاحقًا | سرعة عالية بلا مشروع منفصل، يعيد الخدمات، مسار ترقية واضح للأوفلاين/SPA | يحتاج انضباطًا في تصميم الـendpoints |

**التوصية:** **الخيار (ج)** الآن — `PosController` + صفحة كاشير touch-first داخل CrossBuy تستدعي endpoints JSON نظيفة، مع **عزل حالة الطلب** (order buffer على العميل) بحيث تُضاف الأوفلاين لاحقًا دون إعادة بناء. 
**الأوفلاين:** المرحلة الأولى **online عبر LAN** (المحطات تخاطب الخادم المحلي)؛ الأوفلاين الكامل (طابور محلي + مزامنة + حل تعارض) **مؤجّل لمرحلة تصلّب لاحقة** (تعقيد كبير، لا يُبنى مبكرًا). التصميم يعزل حالة الطلب من الآن ليُصبح ممكنًا.

## 2) رسم المكان (Floor Plan) — نموذج البيانات

| الكيان | الحقول (مقترحة) | الغرض |
|---|---|---|
| `FloorZone` | LocationId(=Branch), Code, Name, Sort | مناطق/أقسام (صالة، تراس، VIP) لكل موقع |
| `FloorTable` | LocationId, ZoneId, Code, Seats, **X, Y, W, H, Shape** (مربّع/دائري), IsActive | طاولة بموضع/حجم لرسم بصري + عدد مقاعد |

- **التخزين:** إحداثيات (X/Y/W/H) تُرسم في محرّر بصري (drag على شبكة) وتُعرض للكاشير كخريطة.
- **الربط بالطلب:** `PosOrder.TableId` (nullable — Takeaway/Delivery بلا طاولة). **حالة الطاولة** مشتقّة: متاحة / مشغولة (طلب مفتوح) / محجوزة — لا تُخزَّن كحقل دائم بل تُحسب من الطلبات المفتوحة (مصدر واحد للحقيقة).
- الطاولة **لا تحمل رصيدًا ماليًا**؛ هي مرجع تشغيلي فقط.

---

## 3) دورة الطلب

```
فتح طاولة/طلب (Open) ─► إضافة أصناف (Lines) ─► إرسال للمطبخ (Sent→KDS) ─► تقديم (Served)
      ─► دفع (Pay: كامل/مقسّم) ─► إقفال (Closed = فاتورة بيع + مخزون + GL)
```
- `PosOrder` { LocationId, BrandId (من الموقع), TableId?, Type (DineIn/Takeaway/Delivery), Status (Open/Sent/Served/Paid/Closed/Void), WaiterEmployeeId, GuestCount, SubTotal/Tax/Service/Discount/Grand, OpenedAt/ClosedAt, InvoiceId? }.
- `PosOrderLine` { OrderId, ItemId, Qty, UnitPrice (من التسعير), Modifiers/Notes, CourseNo, **KdsStatus** (Pending/Preparing/Ready/Served), VoidReason? }.
- **KDS:** تذكرة المطبخ = عرض على السطور ذات `KdsStatus` — «إرسال» ينقل Pending→Preparing ويظهرها على شاشة المطبخ؛ المطبخ يعلّمها Ready؛ النادل Served.
- **تقسيم/نقل/دمج الحساب:**
  - **نقل:** تحريك سطور من طلب/طاولة إلى أخرى (تحديث OrderId/TableId).
  - **تقسيم:** توليد طلب فرعي بجزء من السطور أو بمبلغ (split by line / by amount / by guest).
  - **دمج:** ضمّ طلبَي طاولتين في واحد.
  - قاعدة: التقسيم/النقل/الدمج **قبل التسوية** (على الطلب المفتوح)؛ بعد الفاتورة لا تعديل (مرتجع/إشعار دائن فقط).

---

## 4) الربط بالنواة (عند التسوية — دون كسر الثوابت)

عند **الدفع/الإقفال** يتحوّل `PosOrder` إلى الأحداث القائمة ذرّيًا:
1. **فاتورة بيع** عبر `ReceivableService.CreateSalesInvoiceAsync` (سطور الأطباق) → إيراد + ض.ق.م + **العميل/النقدية**، بعملة الموقع، **بُعد Brand + Project اختياري**.
2. **خصم المكوّنات (backflush):** كل طبق صنف مركّب → بيعه يصرف مكوّناته من المخزون بالتكلفة عبر `StockService` → **COGS + تخفيض مخزون** (نفس مسار فاتورة البيع للأصناف المخزنية، والوصفة تُفكَّك للمكوّنات). أطباق تُصنَّع مسبقًا (دفعات مطبخ) تمرّ عبر أوامر التصنيع القائمة.
3. **التسعير:** سعر السطر من **قائمة أسعار العلامة** (`PricingService`) — لا أسعار يدوية عشوائية.
4. **الدفع:** نقدي/بطاقة → سند قبض/إيداع عبر المسار القائم (نقدية/بنك). التقسيم = عدّة مقابضات على فاتورة واحدة أو عدّة فواتير.
- **الثوابت:** لا كتابة GL/مخزون إلا عبر الخدمات؛ POS **لا يرحّل قيودًا بنفسه**. → stock_gl / ar_sub / tb_balanced … تبقى خضراء. الطلب المفتوح **بلا أثر محاسبي** (تشغيلي فقط) حتى الإقفال.

**قرار حاسم — متى يُخصم المخزون؟** (أ) عند التسوية/الفاتورة (حدث محاسبي واحد نظيف) — **موصى به**؛ (ب) عند الإرسال للمطبخ (الاستهلاك الفعلي لحظة الطهي). التوصية (أ): التكلفة والمخزون عند الفاتورة؛ الهدر/الإلغاء يُعالَج كإعدام منفصل. (يُطرح للحسم.)

## 5) تقسيم المنصة لمراحل (كلٌّ يُبنى ويُختبر وحده)

| المرحلة | المحتوى | الإثبات |
|---|---|---|
| **R1 — الأساس التشغيلي** | قائمة الطعام (أطباق كأصناف مركّبة بوصفات) + `PosOrder` بسيط: فتح→إضافة→دفع→**فاتورة+COGS+GL** بلا طاولات/مطبخ (نمط takeaway) | يثبت الربط بالنواة + الثوابت خضراء (dev test: طلب→فاتورة+backflush) |
| **R2 — الصالة والطاولات** | `FloorZone`/`FloorTable` + محرّر رسم + طلب dine-in مرتبط بطاولة + تقسيم/نقل/دمج | طاولة مفتوحة/مشغولة صحيحة؛ نقل/تقسيم يحافظ على الإجماليات |
| **R3 — شاشة المطبخ (KDS)** | إرسال للمطبخ + شاشة KDS (Preparing/Ready) + كورسات/ملاحظات | تذكرة تظهر/تتحدّث؛ لا أثر GL |
| **R4 — المدفوعات والوردية** | تقسيم فاتورة/تعدّد وسائل دفع/إكرامية + **وردية/درج نقدية + تقرير Z** | إقفال وردية متوازن؛ نقدية الدرج == المقبوضات |
| **R5 — التصلّب** | طباعة إيصال/مطبخ، أجهزة، **أوفلاين (طابور+مزامنة)**، هوية العلامة على الإيصال | مرونة انقطاع الشبكة |

**البدء المقترح:** **R1** — أصغر مسار يثبت أن «طلب مطعم = فاتورة + backflush + GL + Brand + تسعير» بلا كسر ثوابت، قبل الاستثمار في الطاولات/المطبخ.

## 6) المشترك (قابل للتعميم) مقابل الخاص بالمطعم

| مشترك (تجزئة/كافيه لاحقًا) | خاص بالمطعم |
|---|---|
| قوقعة الكاشير (شاشة اللمس + حالة الطلب) | رسم المكان + الطاولات |
| خط الأنابيب: **طلب → فاتورة + COGS + GL + Brand + تسعير** | شاشة المطبخ KDS + الكورسات/التتبّع |
| المدفوعات/الوسائل + الوردية/الدرج + تقرير Z | تقسيم/نقل/دمج حساب الطاولة |
| القائمة/الأصناف + الإيصال + هوية العلامة | أنواع dine-in/takeaway/delivery + النادل/عدد الضيوف |
| **الأصناف المركّبة/الوصفات (backflush)** | «الطبق» كوصفة مطبخ (نفس آلية BOM المشتركة) |

**التعميم لاحقًا:** التجزئة تعيد استخدام كل «المشترك» وتستبدل الطاولات/المطبخ بـ **مسح باركود سريع + أوزان + كاشير سريع**؛ الكافيه = مطعم مبسّط (طاولات اختيارية، بلا كورسات). لذا نبني R1 (المشترك) صلبًا، ثم R2/R3 (الخاص) كطبقة فوقه — فالتعميم يصبح إزالة/استبدال الطبقة الخاصة لا إعادة بناء.

## 7) القرارات الكبيرة المطلوب حسمها قبل R1
1. **معمار الكاشير:** (ج) هجين داخل MVC — موافقة؟
2. **الأوفلاين:** online/LAN الآن، أوفلاين مؤجّل لـ R5 — موافقة؟
3. **توقيت خصم المخزون:** عند التسوية (أ) لا عند الإرسال للمطبخ — موافقة؟
4. **الطبق = صنف مركّب بوصفة** يُفكَّك عند البيع (backflush عبر آلية التصنيع القائمة) — موافقة؟
5. **حالة الطاولة محسوبة** من الطلبات المفتوحة لا مخزّنة — موافقة؟
6. **نطاق R1:** أصغر مسار (بلا طاولات/مطبخ) لإثبات الربط بالنواة أولًا — موافقة؟
