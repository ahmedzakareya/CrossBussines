### The generator now validates itself

Integrity validation runs **before any file is written** and exits non-zero on failure: duplicate ids across all ten collections, field arity per row, status vocabulary, and every capability→phase, capability→decision, capability→dependency, phase→screen, phase→decision, phase→prerequisite and dependency→endpoint reference.

It caught **two real defects on its first two runs**:

1. **`SRC-01` carried 23 values against a 22-field schema.** `zip()` truncates silently, so its `RecommendedPhase` had become `"R-95"` — a risk id — and its evidence field was lost. The CSV looked fine; the phase spread is what exposed it.
2. **`PLT-08` referenced `D-22`**, a decision id that no longer existed after the deployment decisions were renumbered to D-38/39/40.

Both would have shipped as plausible-looking rows. This is the same lesson as the earlier `D-12` collision: **referential defects in a hand-maintained dataset are invisible to proofreading and trivial for a validator.**

## 4. What this increment corrected

**The SQL governance framing.** The previous assessment reported no reliable answer to which slices are applied. Accurate for the **applied** side — and it remains the core risk, because `platform_schema_history.sql` has never been applied. But it understated the **authored** side: `CrossBuy/deploy/sql/manifest.json`, generated by `scan-sql-manifest.ps1`, already registers **all 115 scripts** with SHA-256, apply rank, guard analysis and an idempotency verdict, and already records the 4 divergent duplicates with its own warning that `apply <name>.sql` is ambiguous.

The governance design therefore **extends** that registry. Designing a parallel one would have recreated precisely the defect the two SQL trees demonstrate — two implementations of one concept, drifting apart.

**Two facts surfaced that change R1's scope:**

* **`hm16_rename_grni.sql` is classified `review`** — a mutating script with no re-run guard that nobody has read, sitting in the tree. `script.sql` is `not-deployable`. (RSK-21)
* **`deploy/README.md` states provisioning is BACKUP/RESTORE of `CrossBuyDB2`**, not script replay, because EF migrations are broken and roughly 90 ad-hoc scripts in `C:/temp` built the schema — a third source of truth outside the repository. R1 must reconcile the restore path with the slice path. (RSK-22)

**A risk designed against rather than discovered later.** **RSK-23**: a unified cross-module surface is exactly where an authorization shortcut gets introduced — one efficient joined query returning what the user could not see module by module. The Workspace adds no permissions, delegates every read, and carries per-module delegation tests as an R3 gate.

## 6. Declared limitations

**1 · Ownership boundaries are decided; the owners are not named.** D-32 and D-33 settle what Tasks, Calendar and Communication each own. They do not say which tab holds them. `TAB-5` is registered as **UNASSIGNED** with two live hosted services, and `TAB-0` Integration Owner as **to be appointed**. Both are R1 actions requiring an owner, not an author.

**2 · The brand conflict is resolved in direction, not in code.** D-36 makes CrossBusiness Blue canonical. `crossbuy-brand.css` still applies green and gold across 327 views and was **not modified**, as instructed. D-37 governs the rollout and is **open**. Until it is decided, new and legacy screens will look like two products (RSK-24).

**3 · The Mermaid diagrams use the status palette, not the brand palette.** Their colours encode Verified / Foundation / Legacy / Partial / Blocked / Planned. This is stated in doc 06 so the diagrams are not mistaken for a brand reference.

**4 · Complexity is expressed in bands, not dates.** No evidence supports calendar precision, and inventing it would be the kind of false confidence this whole reassessment exists to remove.
