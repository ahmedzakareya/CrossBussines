### A correction to the previous assessment

The Roadmap v2 assessment reported that there is *"no reliable answer to which slices are applied"*. That is accurate for the **applied** side and remains the core risk. But it understated what already exists on the **authored** side, and the difference changes the design.

**`CrossBuy/deploy/sql/manifest.json` already is a slice registry**, generated by `CrossBuy/deploy/scan-sql-manifest.ps1`, scanning the whole repository. Per script it records:

`path · name · bytes · encoding · sha256 · rank (apply order) · guards · mutations · unguardedBatches · idempotency · reviewVerdict · reviewEvidence · excludedFromDeploy · excludedReason`

And it already classifies:

| Classification | Count | Meaning |
|---|---|---|
| `guarded` | 92 | every mutating batch carries a recognised re-run guard |
| `guarded-by-predicate` | 7 | no textual guard, but read and judged re-runnable |
| `review` | **1** | a mutating batch with **no guard that nobody has read — DO NOT DEPLOY** |
| `not-deployable` | **1** | read and judged unsafe to re-run |
| `no-mutation` | 14 | changes nothing |
| `excludedFromDeploy` | 3 | must never run in a routine deployment |

It also already records the four divergent duplicates, with its own warning: *"duplicateNames with identical=false are the real hazard: the same file name in two trees with different content, so 'apply `<name>`.sql' is ambiguous."*

**So the governance design must extend this, not replace it.** Building a parallel registry would recreate the exact defect the SQL trees already demonstrate — two implementations of one concept, drifting.

### Two further facts that change the picture

**`hm16_rename_grni.sql` is classified `review`** — an unguarded, unread, mutating script sitting in the tree (RSK-21). **`script.sql`** at the repository root is `not-deployable`. Both must be resolved or formally excluded before any environment promotion.

**`deploy/README.md` states the authoritative provisioning method is BACKUP/RESTORE of `CrossBuyDB2`, not script replay** — because EF migrations are broken and the schema was built with roughly 90 ad-hoc scripts in `C:/temp` that "cannot be safely or verifiably linearized". That is a **third source of truth, outside the repository** (RSK-22). Governance that ignores it would describe a build path nobody uses.

## 2. Decisions

### D-38 — Canonical SQL deployment root — **APPROVED**

**`CrossBuy/deploy/sql` is the canonical AUTHORED-slice root.**

Evidence: the governance tooling (`scan-sql-manifest.ps1`, `report-schema-history.ps1`) and `manifest.json` already live at `CrossBuy/deploy/`; all newer platform work (business events, bootstrap policies, reporting, communication, hyper, tasks, calendar) was authored there.

**`deploy/` is retained and re-labelled the deployment PACKAGE root** — not an authoring root. It holds generated artifacts (`fresh/`, produced by `gen_fresh_db.ps1`), operational scripts (backup, purge), the server README and `deploy.ps1`.

**No file is moved in this increment.** Migration of the 53 package-tree module slices into the canonical root is an R1 action, executed slice by slice with hash verification.

### D-39 — Divergent same-name reconciliation — **APPROVED direction**

Each of the four pairs is **diffed and read by its owner, then superseded by ONE reconciled slice with a new SliceId.** Neither copy simply wins.

Choosing by modification time or by location would be guessing about schema, and a wrong guess here silently changes a POS table. The manifest already tells us these are ambiguous; it cannot tell us which is correct.

The `review` and `not-deployable` scripts are resolved by the same rule: read by the owner, then either guarded and re-classified, or formally excluded with a recorded reason.

### D-40 — PlatformSchemaHistory — **APPROVED direction**

The manifest is the **authored** registry. `PlatformSchemaHistory` is the **applied** registry. Neither replaces the other.

## 3. Immutable slice identity

Every slice carries, in the authored registry and in the applied record:

| Field | Source | Note |
|---|---|---|
| `SliceId` | assigned on claim | Immutable. Never reused, never renumbered. |
| `Filename` | file | May change; `SliceId` does not follow it |
| `SHA256` | content | The identity that matters — already in `manifest.json` |
| `Module` | owning tab | From the Tab Ownership Register |
| `Owner` | tab | Accountable for content and reconciliation |
| `Dependencies` | declared | Slices that must be applied first |
| `Rank` | manifest | Apply order; equal ranks are mutually independent |
| `Idempotency` | manifest | guarded / guarded-by-predicate / review / not-deployable / no-mutation |
| `AppliedDate` | applied record | Per environment |
| `Environment` | applied record | Dev / Test / Prelive / Production |
| `Result` | applied record | Success / Failed / Skipped, with message |

**`SliceId` + `SHA256` together are the identity.** A slice whose content changes after being applied somewhere is not the same slice — that is the drift case below.

## 4. PlatformSchemaHistory design

```
PlatformSchemaHistory
  SliceId          nvarchar   NOT NULL
  Filename         nvarchar   NOT NULL
  Sha256           char(64)   NOT NULL
  Module           nvarchar   NOT NULL
  Owner            nvarchar   NOT NULL
  DependsOn        nvarchar   NULL      -- comma-separated SliceIds
  Rank             int        NOT NULL
  AppliedAtUtc     datetime2  NOT NULL
  AppliedBy        nvarchar   NOT NULL
  Environment      nvarchar   NOT NULL  -- Dev | Test | Prelive | Production
  Result           nvarchar   NOT NULL  -- Success | Failed | Skipped
  Message          nvarchar   NULL
  PRIMARY KEY (SliceId, Sha256, Environment)
```

Rules:

1. **It is the first slice applied in every environment.** A database with no history table has no governed state.
2. It is **append-only**. A re-application appends a row; it never updates one.
3. It is written by the deployment process, never by application code.
4. It is **additive and idempotent**, like every slice — never an EF migration.

## 5. Drift behaviour

Drift detection compares the authored registry (`manifest.json`) against the applied registry (`PlatformSchemaHistory`) for a given environment.

| Condition | Detection | Behaviour |
|---|---|---|
| **Missing slice** — authored, never applied | in manifest, absent from history | **Report and block promotion.** Apply in rank order. |
| **Changed applied slice** — content differs from what was applied | same `SliceId`, different `SHA256` in history | **BLOCK.** The applied database no longer matches the authored source. Requires an owner decision: supersede with a new `SliceId`, or restore. Never silently re-apply. |
| **Duplicate SliceId** — two files claim one id | manifest scan | **BLOCK at authoring time.** The registry claim is the guard. |
| **Same filename, different hash** — the current 4 pairs | `duplicateNames` with `identical: false` | **BLOCK.** "Apply `<name>`.sql" is ambiguous. Resolve per D-39. |
| **Out-of-order dependency** | `DependsOn` not present in history | **BLOCK.** Apply the dependency first. |
| **Unreviewed script** | `idempotency: review` | **BLOCK.** Not deployable until read and guarded. |
| **Excluded script present in a run** | `excludedFromDeploy: true` | **BLOCK.** These never run in a routine deployment. |

The consistent answer is **block, not warn**. A warning in a deployment pipeline is a message nobody reads at 2 a.m.; and the platform already has a precedent — the bootstrap policy slice's drift detection **throws** rather than logging.

```mermaid
  D --> T["Test"]:::d
  T --> P["Prelive"]:::d

  classDef d fill:#1d6b5a,color:#fff;
  classDef r fill:#13433a,color:#fff;
```

| Environment | Entry condition |
|---|---|
| **Dev** | Slice claimed with a `SliceId`; manifest regenerated; idempotency is not `review` or `not-deployable` |
| **Test** | Applied cleanly in Dev; second-apply idempotency proved; history row `Success` |
| **Prelive** | Zero drift against Test; all dependencies applied; owner sign-off |
| **Production** | Zero drift against Prelive; rollback plan recorded; **Integration Owner approval** |

A slice may not skip an environment. Promotion is by `SliceId` + `SHA256`, so promoting "the latest version of the file" is not expressible — which is the point.

### The restore path

Because provisioning today is backup/restore of `CrossBuyDB2` (RSK-22), a restored database must be **stamped**: `PlatformSchemaHistory` is populated to reflect what the restored image actually contains, verified against the manifest. An unstamped restore is an ungoverned database and may not be promoted.

Reconciling the restore path with the slice path — deciding which is authoritative for a *new* environment — is an explicit R1 deliverable.

## 7. Rollback and forward-fix

| Situation | Rule |
|---|---|
| Slice fails mid-apply | Transactional slices roll back; the history row records `Failed` with the message. Fix and re-apply — do not hand-patch the database. |
| Slice applied, defect found in Dev/Test | **Forward-fix** with a new `SliceId`. Never edit an applied slice — that is the "changed applied slice" drift case. |
| Slice applied to Production, defect found | **Forward-fix only.** A corrective slice, reviewed and promoted through every environment. |
| Data corrupted by a slice | Restore from backup. Corrections to *business* data follow the platform rule: **reverse, never delete**. |
| Structural change must be undone | A new slice that reverses it, with its own `SliceId`. There is no "down" script. |

There is no down-migration by design. The platform's own discipline — additive idempotent SQL, corrections by reversal — extends here: a down script is a second, less-tested code path that runs only when things are already going wrong.

## 8. SQL ownership and review gates

| Gate | Requirement |
|---|---|
| **Claim** | `SliceId` claimed in the registry before authoring. Duplicate claims blocked. |
| **Authoring** | Idempotent and additive. Every mutating batch carries a re-run guard, or is read and justified as `guarded-by-predicate`. |
| **Owner review** | The owning tab reviews; slices touching `JournalEntryService` or `StockService` tables additionally require owner coordination. |
| **Manifest** | `scan-sql-manifest.ps1` re-run; `manifest.json` regenerated, never hand-edited. |
| **Integration gate** | Slice appears in the registry, is not `review`/`not-deployable`, and its dependencies are declared. |
| **Promotion** | Per §6. |
| **Cross-tab** | A slice touching another tab's tables requires that tab's sign-off. |

## 9. R1 exit criteria

R1 is complete when all of the following hold:

1. All four tabs' work is committed.
2. `CrossBuy/deploy/sql` is the canonical authored root; `deploy/` is labelled the package root.
3. The 53 package-tree module slices are migrated with hash verification, or explicitly scheduled.
4. The 4 divergent pairs are reconciled into single superseding slices.
5. `hm16_rename_grni.sql` (`review`) and `script.sql` (`not-deployable`) are resolved or formally excluded.
6. `PlatformSchemaHistory` is designed, authored and applied as the first slice in each environment.
7. Every environment's applied state is stamped and reconciled against the manifest.
8. The restore path is reconciled with the slice path, with an authoritative choice recorded.
9. Drift detection blocks on all seven conditions in §5.
10. Per-tab worktrees, the protected integration branch and the 12-point integration gate are in force in CI.
11. Zero build breaks for one full integration cadence.

**Only then do Reporting, Communication and Construction schemas get activated in R2.**
