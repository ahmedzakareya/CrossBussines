هل نُبقي النظام على ASP.NET MVC أم نحوّله إلى React؟

القرار: التحويل إلى React + واجهة برمجية (API)

لأن الهدف نظام ERP متكامل (موارد بشرية + حسابات كاملة + مخازن كاملة)، والبقاء على شاشات Razor المونوليثية لن يصمد أمام هذا الحجم.

الواجهة: React الخادم: ASP.NET Core Web API الموبايل: Flutter مصدر واحد للبيانات

★ الخلاصة في 4 نقاط

  • القرار: نحوّل الواجهة إلى React، ويبقى الخادم ASP.NET Core لكن كـ Web API (JSON) بدل صفحات Razor.
  • السبب: الـ ERP = مئات الشاشات المعقّدة المتكرّرة العناصر؛ React يعيد استخدام المكوّنات، Razor المونوليثي لا.
  • الطريقة: تحويل تدريجي موديول-بموديول (نمط Strangler)، مش إعادة كتابة دفعة واحدة.
  • المكسب: نفس الـ API يخدم الويب (React) والموبايل (Flutter) ومستقبلًا التكاملات والتقارير — تُكتب قواعد العمل مرة واحدة.

1 تقييم الوضع الحالي

الشكل ممتاز (Metronic)، لكن البِنية تحت السطح هي مكمن الخطر مع التوسّع.

  • الشاشة الواحدة قد تتجاوز 6000 سطر فيها HTML + CSS + JavaScript مختلطين داخل ملف Razor واحد.
  • المنطق يعتمد على الجلسات (Session)، والاستجابات JSON تُكتب بشكل مخصّص لكل صفحة (غير موحّد).
  • إعادة استخدام المكوّنات شبه معدومة — كل شاشة تُبنى من الصفر تقريبًا.
  • تشابك منطق الواجهة مع الخادم يجعل الصيانة والتطوير المتوازي صعبًا كلما كبر الفريق والنظام.
المعنى: النظام يعمل جيدًا اليوم كـ موديول HR أول، لكن مضاعفته إلى حسابات ومخازن على نفس الأسلوب يضاعف الديون التقنية ويُبطئ كل إضافة لاحقة.

2 لماذا React مناسب لـ ERP تحديدًا؟

ليست موضة — بل تطابق مع طبيعة أنظمة ERP.

  • إعادة استخدام المكوّنات: جداول البيانات، القوائم المنسدلة (Lookups)، منتقيات التاريخ، دورات الاعتماد — تُبنى مرة وتُستخدم في كل الموديولات. هذا جوهر الـ ERP.
  • شاشات كثيفة وتفاعلية: فلاتر، تابات متعددة، تحقق فوري، تحديث لحظي — React يتعامل معها بسلاسة وأداء عالٍ.
  • فصل الاهتمامات: منطق العمل والبيانات في الـ API، والواجهة منفصلة — أوضح وأأمن وأسهل اختبارًا.
  • تجربة مستخدم القوة: المحاسب وأمين المخزن يقضون يومهم داخل النظام؛ تنقّل SPA السريع يرفع إنتاجيتهم.
  • نظام بيئي ناضج: مكتبات بمستوى ERP (جداول متقدمة، إدارة حالة، نماذج، تقارير).
  • متوافق مع وضعك: لديك بالفعل تطبيق React قائم (al-react) و API منفصل — التحويل يوحّد المسار بدل تشتيته.

5 خطة التحويل التدريجي (Strangler)

لا لإعادة الكتابة دفعة واحدة — فهي أكثر أسباب فشل المشاريع.

1

بناء طبقة الـ API أولًا

توحيد المصادقة (JWT) وتغطية موديول HR بالكامل بـ endpoints منظّمة وموثّقة (Swagger).

2

تحويل موديول HR كـ Proof of Concept في React

إثبات النمط (شاشات، مكوّنات مشتركة، حالة) قبل التوسّع.

3

بناء الموديولات الجديدة في React مباشرة

الحسابات الكاملة والمخازن تُبنى React-first فوق نفس الـ API.

4

الإحلال التدريجي

يظل MVC القديم يعمل حتى تحل شاشات React محله موديولًا تلو الآخر، دون توقف للعمل.

6 المخاطر وكيف نتجنّبها

  • استثمار أكبر في البداية → نوزّعه على مراحل، ونبدأ بالـ API الذي يخدم الموبايل أيضًا (عائد مزدوج).
  • منحنى تعلّم الفريق → لديك فريق React قائم بالفعل (al-react)، فالفجوة محدودة.
  • إغراء إعادة الكتابة الكاملة → ممنوع؛ نلتزم بالتحويل التدريجي.
  • ازدواج المنطق → القاعدة الذهبية: كل قواعد العمل في الـ API فقط، الواجهات تعرض ولا تقرّر.

7 قرارات ثابتة (لا تتغيّر)

  • الخادم يبقى C# / ASP.NET Core — لا تحويل إلى Node؛ نحافظ على خبرة الفريق و EF Core ومنطق العمل الحالي.
  • قاعدة البيانات تبقى SQL Server كما هي.
  • الموبايل يبقى Flutter (يعمل بالفعل) — والويب React — والاثنان على API واحد.
