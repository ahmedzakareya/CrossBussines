# CrossBuy — المشاريع والمقاولات — P3: التنفيذ ونِسب الإنجاز (تصميم فقط)

> **الحالة:** تصميم بانتظار مراجعتك. **لا كود بعد.** يُبنى فوق P0 (المشروع) و P1 (BOQ).

---

## 1. النطاق والمبادئ

- **تشغيلي بحت — لا محاسبة.** نِسب الإنجاز والكميات المنفّذة **تقديرية/تشغيلية**، لا تُنشئ أي قيد يومية. الفوترة والاحتجاز واسترداد المقدّم كلها في **P المستخلصات** لاحقًا. **لا كاتب محاسبي جديد.**
- **الأساس للمستخلصات.** الهدف الأساسي من P3 أن يكون **الحصر الميداني (المقايسة)** الذي يبني عليه المستخلص: كمية منفّذة تراكمية لكل بند، بتاريخها.
- **مرن (المستخدم يحدّد).** لا نفترض وحدات ولا طريقة قياس؛ نتبع بنود BOQ الموجودة (حرّة أصلًا).
- **النسب بـ `ProjectId`** — لا بُعد جديد. مربوط بالبنود عبر `BoqItemId`.
- **`inv-test-integrity = 0`** بعد كل تغيير (لا يوجد ما يمسّ المخزون/GL أصلًا).

## 2. نقاط الحسم (خيارات + توصية)

### 2-1 مستوى تتبّع النسبة: المشروع كله؟ أم لكل بند BOQ؟

| الخيار | الوصف | العيب |
|---|---|---|
| أ) نسبة واحدة للمشروع | المستخدم يدخل % واحدة للمشروع | لا يصلح أساسًا للمستخلص (المستخلص دائمًا لكل بند) |
| **ب) لكل بند BOQ (موصى به)** | كمية منفّذة/نسبة لكل بند، والنسبة الكلية تُشتقّ تلقائيًّا | — |

**✅ التوصية: (ب) لكل بند BOQ (البنود الورقية/leaf).**
- المستخلص في المقاولات **دائمًا لكل بند** (كمية منفّذة × سعر الوحدة). الخيار (أ) لا ينتج مستخلصًا إطلاقًا.
- **النسبة الكلية للمشروع تُحسب تلقائيًّا** = Σ(قيمة المنفّذ) ÷ Σ(قيمة BOQ) — مرجّحة بالقيمة، لا متوسّط حسابي (بند بمليون ≠ بند بألف).
- بنود العناوين/الأقسام (`ParentId=null` ولها أبناء) لا تُقاس مباشرة — تتجمّع من أبنائها.
- **مرونة (fallback):** مشروع **بلا BOQ** → نسمح بإدخال **نسبة واحدة يدوية على مستوى المشروع** فقط، حتى تعمل الأنشطة غير المُبوّبة. (إن وُجد BOQ → القياس لكل بند.)

### 2-2 كيف تُحسب النسبة: يدوي؟ أم كمية منفّذة ÷ كمية BOQ؟

| الخيار | الوصف | العيب |
|---|---|---|
| أ) يدوي (% لكل بند) | المستخدم يكتب % لكل بند | ذاتي، لا يربط بقيمة قابلة للتدقيق |
| ب) كمية منفّذة ÷ كمية BOQ | يدخل الكمية المنفّذة، والنسبة تُحسب | لا يناسب البنود المقطوعية (Lump‑sum) |
| **ج) كمية أساسًا + تجاوز يدوي (موصى به)** | كمية منفّذة تراكمية ← % تلقائي؛ ويُسمح بـ% يدوية لبنود المقطوعية | — |

**✅ التوصية: (ج).**
- **الأساس = الكمية المنفّذة التراكمية** لكل بند ← `% = المنفّذة ÷ كمية BOQ` (بحدّ أقصى 100%). هذه الطريقة المعيارية وتعطي **قيمة منفّذة قابلة للتدقيق** = الكمية المنفّذة × سعر الوحدة (أساس المستخلص).
- **تجاوز يدوي للنسبة** لكل سطر: للبنود المقطوعية/غير القابلة للقياس (مثل «تجهيز الموقع» مقطوعية) — يكتب % مباشرة وتُحسب القيمة = % × قيمة BOQ للبند.
- الافتراضي كمية؛ وإدخال % يدوية يتجاوزه لذلك السطر فقط.

### 2-3 السجلّ الزمني: كل قياس بتاريخه (أساس المستخلصات)

**✅ التوصية: لقطات تراكمية (Cumulative snapshots).**
- كل **قياس/حصر** = مستند مؤرَّخ (رأس + سطور)، كل سطر يحمل **الكمية المنفّذة التراكمية** لبند حتى تاريخه.
- النظام يحسب **فرق الفترة** = التراكمي الحالي − تراكمي القياس السابق. (هذا بالضبط **المستخلص التراكمي مقابل الجاري** في المقاولات.)
- **الإنجاز الحالي للمشروع = أحدث قياس.** التاريخ محفوظ بالكامل.
- لاحقًا: **المستخلص رقم n** يشير إلى قياس، ويُفوتر **فرق الفترة** (ناقص المحتجز، ناقص استرداد نسبة من المقدّم) — كلها في P المستخلصات، لا هنا.

### 2-4 حالة القياس (قفل)

**✅ التوصية: `Status = Draft/Confirmed` (بسيط).**
- **Draft:** قابل للتعديل/الحذف بحرية (تشغيلي، لا GL).
- **Confirmed:** لقطة تاريخية مجمّدة (يُقفل عند إصدار مستخلص عليه لاحقًا). في P3 يكفي الحقل؛ ربط المستخلص يأتي لاحقًا.
- يُسمح بتعديل أحدث قياس Draft فقط؛ ولا يُسمح بقياس جديد بتاريخ أقدم من آخر Confirmed.

### 2-5 تجاوز كمية BOQ (أوامر التغيير)

**✅ التوصية:** نسمح بإدخال كمية منفّذة **أكبر** من كمية BOQ (يحدث ميدانيًّا)، **لكن:**
- **النسبة تُعرض بحدّ أقصى 100%** والقيمة المنفّذة للتجميع **تُقصّ عند قيمة BOQ** (لا نفوتر تجاوزًا بلا أمر تغيير).
- نعرض **تنبيهًا** على السطر المتجاوز. **أوامر التغيير (Variation Orders)** بند مؤجّل مستقل.

### 2-6 طريقة تجميع النسبة الكلية

**✅ التوصية: مرجّحة بالقيمة.**
`النسبة الكلية = Σ(قيمة المنفّذ لكل بند) ÷ Σ(قيمة BOQ لكل بند)`. تُخزَّن كلقطة على رأس القياس (للتاريخ والأداء).

## 3. نموذج البيانات (مقترح — إضافي، لا يمسّ الموجود)

**رأس القياس — `ProjectProgress`:**
| الحقل | النوع | ملاحظة |
|---|---|---|
| ID, CompanyID | int | |
| ProjectId | int | → Project (P0) |
| MeasurementNo | int | تسلسل لكل مشروع (1,2,3…) |
| MeasurementDate | date | تاريخ الحصر |
| Note | string? | ملاحظة |
| Status | string | Draft / Confirmed |
| OverallPercent | decimal(9,4) | **لقطة** محسوبة |
| ExecutedValue | decimal(19,4) | **لقطة** Σ قيمة المنفّذ التراكمي |
| CreatedAt / CreatedBy | | |

**سطر القياس — `ProjectProgressLine`:**
| الحقل | النوع | ملاحظة |
|---|---|---|
| ID, ProgressId | int | → ProjectProgress |
| BoqItemId | int | → BoqItem (P1) — البند الورقي |
| CumulativeQty | decimal(19,4) | الكمية المنفّذة **التراكمية** |
| ManualPercent | decimal(9,4)? | تجاوز مقطوعية (اختياري) |
| Note | string? | |

**`[NotMapped]` محسوبة (لا تُخزّن على السطر):** `Percent` = ManualPercent ?? min(CumulativeQty ÷ boqQty, 100) ؛ `ExecutedValue` = (ManualPercent ? %×قيمةBOQ : min(CumulativeQty, boqQty)×سعرالوحدة).

> **مرونة بلا BOQ:** إن كان المشروع بلا BOQ، القياس يحمل سطرًا واحدًا بـ `BoqItemId=null` + `ManualPercent` (نسبة المشروع اليدوية). (نجعل `BoqItemId` nullable.)

**SQL:** `deploy/sql/projects_p3_progress.sql` — CREATE للجدولين (idempotent)، لا ALTER على شيء قائم. DbSets: `ProjectProgresses`, `ProjectProgressLines`.

## 4. الخدمة `IProgressService` (تشغيلية — لا GL)

- `GetMeasurementsAsync(company, project)` — قائمة القياسات (رأس فقط) مرتّبة بالتاريخ.
- `GetMeasurementAsync(company, id)` — رأس + سطور + بنود BOQ للعرض.
- `BuildEditModelAsync(company, project, measurementId?)` — يرجّع **كل بنود BOQ الورقية** لهذا المشروع + التراكمي **السابق** لكل بند (من آخر قياس قبله) لعرض «سابق/حالي/فرق».
- `SaveMeasurementAsync(company, project, date, note, List<line>)` — يحفظ لقطة تراكمية، يحسب OverallPercent/ExecutedValue، يُنشئ MeasurementNo تلقائيًّا. (Draft) — **لا قيود.**
- `ConfirmAsync / DeleteAsync` (Draft فقط).
- `GetProjectProgressAsync(company, project)` — النسبة الحالية = أحدث قياس (تُستخدم لاحقًا في المستخلصات ولوحة المشروع).

## 5. كيف يغذّي المستخلصات لاحقًا (لا يُبنى الآن — لتأكيد الاتجاه فقط)

المستخلص #n يقرأ قياسًا Confirmed → لكل بند: **قيمة الفترة = تراكمي حالي − تراكمي مستخلص سابق** → ثم (في P المستخلصات فقط): احتجاز % + استرداد نسبة من المقدّم (2104) + صافٍ مستحق → عندها فقط تُنشأ القيود عبر الخدمات الموجودة. **P3 يوفّر الأرقام التشغيلية فقط.**

## 6. الشاشة (اقتراح — بانتظار تصميمك؛ لا أجتهد)

نقطة الدخول: زر **«الإنجاز»** على صف المشروع (بجانب زر BOQ) ← صفحة إنجاز المشروع.

الصفحة جزآن، كلاهما **بأنماط معتمدة موجودة** (لا HTML/CSS جديد):

- **(أ) سجلّ القياسات** — بطاقة قائمة (نمط قوائم الحسابات): رقم/تاريخ/النسبة الكلية/قيمة المنفّذ/الحالة + زر «قياس جديد» + فتح/تعديل.
- **(ب) محرّر القياس** — **جدول تحرير inline (نفس نمط سطور BOQ/الفاتورة `.cb-2row`)**: صف لكل بند BOQ ورقي:
  - أعمدة للقراءة: الكود · الوصف · الوحدة · كمية BOQ · سعر الوحدة · قيمة BOQ · **التراكمي السابق**
  - أعمدة للإدخال: **الكمية المنفّذة التراكمية** (+ % يدوية اختيارية)
  - أعمدة تلقائية حيّة: **% · قيمة المنفّذ · فرق الفترة**
  - رأس: تاريخ القياس + ملاحظة. شريط إجماليات حيّ: **النسبة الكلية % · قيمة المنفّذ · قيمة الفترة**.

**سؤالي لك (اختَر تصميم الشاشة):**
1. سجلّ القياسات: **قائمة كاملة + محرّر في صفحة منفصلة** (زر «قياس جديد» يفتح صفحة المحرّر) — أم **قائمة + المحرّر في مودال**؟
2. محرّر القياس: أوافقك على **جدول inline** كنمط سطور BOQ؟ أم تفضّل شكلًا آخر تحدّده؟

## 7. اختبار DevSeed المخطّط: `/api/dev/p3-test`

مشروع + BOQ (بندان) → قياس #1 (كميات جزئية) ثم قياس #2 (كميات أكبر) → يتحقّق: النسبة الكلية مرجّحة صحيحة، فرق الفترة = تراكمي2 − تراكمي1، **صفر قيود يومية جديدة (JE count ثابت)**، ينظّف نفسه. + `inv-test-integrity=0`.

## 8. خارج النطاق / مؤجّل

- **أي قيد محاسبي** (فوترة/احتجاز/استرداد مقدّم) → P المستخلصات.
- **أوامر التغيير (Variation Orders)** وتعديل قيمة العقد → بند مستقل لاحق.
- ربط الكمية المنفّذة بصرف مواد فعلي/عمالة فعلية (P التنفيذ التفصيلي) → لاحق.
- منحنى S / جدول زمني مخطّط مقابل فعلي → لاحق.
